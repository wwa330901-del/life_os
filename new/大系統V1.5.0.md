## 一、本階段目標

從「平台核心做完但沒有任何實際功能」邁向「境為公司空間有一個真正能用的業務模組」，同時把上一版遺留的一個正式環境穩定性問題補起來。

## 二、本階段兩件事

### （一）登入事故修復 + migration 自動化

2026-07-24 下午發生一次事故：Google 登入／密碼登入全部回 500，且登入狀態不會保留。根本原因是兩個問題疊在一起：

1. 新增 `User.isPlatformAdmin` 欄位的 migration 沒有自動套用到正式環境資料庫（Render 的部署流程本來就不會自動跑 `prisma migrate deploy`）
2. 為了補跑 migration 重設了 Supabase 資料庫密碼，但 Render 的 `DATABASE_URL` 環境變數沒有跟著更新

完整的除錯過程、確認方式、最終解法都記錄在 `life_os/docs/問題排除紀錄.md`。修復後**把 migration 自動化**：Render 的 Pre-Deploy Command 是付費限定用不了，改成把 `npx prisma migrate deploy &&` 接到 Start Command 前面，這樣以後每次部署/喚醒都會自動套用新 migration，不用再手動跑。

### （二）境為專案管理系統（第一個功能模組）

使用者決定的產品方向：境為（COMPANY 空間）底下要有「專案管理」入口 → 專案清單 → 點進單一專案看到工期、金額、合約條件、發包狀態、成本控制、專案成員。**Project 是核心實體**，工期（甘特圖排程）只是它第一個做出來的分頁；其餘 5 個分頁這版先做導覽骨架、內容顯示「即將推出」。

排程演算法邏輯直接沿用姊妹專案 `reno_pm`（獨立的 Windows 甘特圖排程 app，本機單人使用）——核心排程/工期計算是純 Dart、零 Flutter 相依，整批移植。但 life_os 是多人協作的雲端平台，所以排程計算搬到後端，改成「讀取時即時計算、不落地儲存」，確保多人同時查看同一專案時日期一致（這是 reno_pm 單機版從來不用解決的問題）。

分五個階段完成，每階段都驗證過才進下一階段：

**Phase 0 — Prisma schema**：新增 `Project`、`WorkItem` 兩個 model（`life_os/apps/api/prisma/schema.prisma`）。`predecessorIds` 用陣列欄位而非 join table（排程器本來就容忍懸空引用，陣列比 FK 更貼近這個語意）；假日行事曆攤平存在 `Project` 上而非另開 model。跑 migration 前先用 Prisma Studio 驗證 `DateTime[] @db.Date` 陣列欄位真的能正常寫入讀出。

**Phase 1 — 後端排程引擎移植**：`reno_pm/lib/core/scheduling/` 系列檔案（`scheduler.dart`、`topo_sort.dart`、`working_day_calculator.dart`、`holiday_calendar.dart`、`taiwan_holiday_calendar.dart`、`work_item_hierarchy.dart`）搬成 `life_os/apps/api/src/projects/scheduling/*.ts`，純 TypeScript、零 Nest/Prisma 相依。6 個 Dart 測試檔的 42 個案例全部 1:1 搬過來，跑 `npm test` 全過。**移植過程中用 curl 實測抓到一個真的 bug**：日期物件用了本機時區建構（`new Date(y,m,d)`），在 GMT+8 機器上序列化回前端會少一天；改成全程 `Date.UTC` 才修好，這個修法已經寫進程式碼註解，日後如果要再碰日期運算要記得這個坑。

**Phase 2 — 後端 CRUD API**：`life_os/apps/api/src/projects/` 底下的 `projects.module.ts` + 三個 controller（`space-projects`／`projects`／`work-items`）+ 對應 service + DTO。權限沿用既有的 `SpacesService.getForUserOrThrow`，不新建 guard。端點涵蓋專案 CRUD、假日行事曆更新、`/schedule`（即時計算）、工項 CRUD + 排序。**全部端點都用 curl 對著境為空間的真實資料驗證過**：巢狀工項＋相依關係、排程日期手算核對、行事曆變更連動位移、母項目刪除連子項一起刪、非成員打 API 拿到 403。

**Phase 3 — 前端唯讀切片**：`ProjectListScreen` → `ProjectDetailScreen`（`TabBar`：工期／金額／合約條件／發包狀態／成本控制／專案成員）→ 工期分頁唯讀渲染。甘特圖 widget（`gantt_painter.dart`／`gantt_header_painter.dart`／`gantt_timeline.dart`）從 reno_pm 搬過來，路徑在 `life_os/apps/windows_app/lib/ui/widgets/projects/gantt/`。`home_screen.dart` 的舊佔位文字換成「專案管理」卡片，只在 `space.type == COMPANY` 時顯示。

**Phase 4 — 前端編輯功能**：`task_table.dart`、`dependency_picker_dialog.dart`、`holiday_calendar_dialog.dart` 從 reno_pm 搬過來，改接後端 API（`ProjectEditorNotifier`，每次編輯都是「打 API → 重新整份 refetch」，不在本機模擬狀態）。文字欄位改成打字完（Enter 或失焦）才送出，不是每個字都打 API。結束日回推工期改用真正的 `WorkingDayCalculator.countWorkingDaysInclusive`（跳過假日），不是天數硬減。

**過程中額外做的視覺修正**：甘特圖原本的配色是 reno_pm 寫死的鮮豔 Tailwind 色（藍/綠/橘/紅…），使用者反饋「太小孩子」，用資料視覺化的正式方法（`dataviz` skill：OKLCH 明度區間、彩度下限、色盲區隔 ΔE、對比度）重新設計了一組跟著元序暖色調主題走的低飽和配色，深淺色模式都驗證過。這組色票在 `life_os/apps/windows_app/lib/ui/widgets/projects/gantt/gantt_colors.dart`。

## 三、目前已完成功能（累積，含 V1.4.0 既有的平台核心）

### 平台核心（V1.4.0 完成，本版無變動）

帳號系統、Email 驗證、Google 登入、個人空間自動建立、公司空間會員骨架、桌面整合與自動更新、Render + Supabase 部署——細節見 `大系統V1.4.0.md`。

### 專案管理系統（本版新增）

- 境為空間首頁有「專案管理」入口，點進去是專案清單
- 可新增專案（名稱／業主／開工日）
- 專案詳情頁是分頁式介面，工期分頁完整可用，其餘 5 個分頁顯示「即將推出」
- 工期分頁：任務表格（可改名、改工期、指定/取消手動起始日、設定前置工項、拖曳同層排序、刪除含子項）＋ 甘特圖（母項目彙總列、依賴箭頭、今日標線、離職日陰影），兩邊共用垂直捲動、點選同步
- 公休日曆設定：每週固定公休、台灣行政院公告假日開關（涵蓋 2026-2027，需要人工每年擴充）、個別加休/補班
- 排程日期一律伺服器即時計算，前端從不自己算，保證多端一致

### 部署

正式環境現在會**自動套用 migration**（接在 Render Start Command 前面），不用再手動跑。目前版本：**v0.6.0**（`life_os/apps/windows_app` `pubspec.yaml` + `installer/life_os.iss`），GitHub Release 已發布並附安裝檔。

## 四、已知限制（尚待解決）

沿用 V1.4.0 的：

1. **Resend 寄信限制**依然存在——只有 `wwa330901@gmail.com` 能收到驗證信，其他人用密碼註冊會卡住（Google 登入不受影響）
2. Render 免費方案閒置喚醒 30-60 秒
3. 角色/欄位層級權限仍是粗粒度（任何空間成員都可讀寫專案）
4. 尚無 LINE、AI 功能

本版新增的限制：

5. **專案詳情頁的 5 個分頁（金額/合約條件/發包狀態/成本控制/專案成員）只有導覽骨架，沒有實際內容**——之後可以像獨立小模組一樣逐一補上
6. **台灣假日表只到 2027 年**，超過涵蓋年份會靜默 fallback 成只看週末，沒有警示（跟 reno_pm 原本行為一致，刻意沒有擴大範圍）
7. **沒有 undo/redo**——reno_pm 的本機復原堆疊在多人協作的伺服器模型下語意不明確（復原可能蓋掉別人剛做的變更），這版直接不做，之後真的要做要重新設計（例如做成操作紀錄而非狀態快照復原）
8. **沒有即時同步（websocket）**——多人同時開同一個專案，只有手動重新整理才會看到另一端的變更
9. **Phase 4 編輯功能還沒有真人親自點過一遍**——這次在本機用真實 API 端點測過（curl 全綠）、`flutter analyze` 乾淨、build 成功也真的啟動看過畫面，但「打字改名、拖曳排序」這類純互動行為受限於這台機器上 OS 層級滑鼠自動化不可靠（懷疑 DPI 縮放問題，UI Automation 語意樹也沒抓到元素），沒能自動化驗證。**下次要做的事：使用者自己實際點一次工期分頁的編輯功能，回報有沒有問題。**
10. **整個 App 的視覺排版還沒有全面重新設計**——使用者反饋現有畫面（登入頁、選空間頁、首頁、管理後台）偏「陽春」，希望更有質感、高級感的管理軟體觀感。已確認方向：**保留現有暖色調詩意風格，但做得更精緻**（字體層級、留白、間距節奏、卡片質感），不是換成 Linear/Notion 那種灰階密度風,也不是 Stripe/Vercel 那種深色科技風。使用者決定**先不做**，等 Phase 4 功能真的驗證過、之後有空再回頭處理——**這是下一步最值得做的事之一**。

## 六、發布流程（沿用，供未來每次使用者可見更新時照做）

1. commit + push 程式碼
2. 版本號同步改 `apps/windows_app/pubspec.yaml` 與 `apps/windows_app/installer/life_os.iss`（`MyAppVersion`，兩處必須一致）
3. `flutter build windows --release`
4. 打包安裝檔：`"C:\Users\chen6\AppData\Local\Programs\Inno Setup 6\ISCC.exe" installer\life_os.iss`（**這台機器上 Inno Setup 裝在使用者層級的 `AppData\Local\Programs`，不在 `Program Files`，之後找不到 `ISCC.exe` 先檢查這裡**，不要誤判成沒裝）
5. `gh release create vX.Y.Z installer/Output/life_os_setup.exe --title vX.Y.Z --notes "..."`
