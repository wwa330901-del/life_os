# 第 3 步：系統技術架構與部署策略

## 一、本階段目標

建立平台第一階段的技術架構，確保：

- 能立即開始開發
- 不需要購買機房或伺服器
- 電腦關機後系統仍可運作
- 未來可搬遷至 NAS、自建伺服器或其他雲端
- 不被任何單一雲端服務綁定
- 具備企業級資訊安全基礎
- 所有新增費用均需事前揭露並取得同意

---

## 二、第一階段技術架構

```text
Windows App（Flutter）
          │
          ▼
NestJS REST API
          │
          ▼
PostgreSQL
          │
          ▼
Storage Adapter
          │
          ▼
Supabase Storage（第一階段）
```

未來儲存可切換為：

```text
Storage Adapter
        │
        ├── Supabase
        ├── NAS
        ├── MinIO
        └── S3
```

因此不需要修改主要商業邏輯。

---

## 三、技術選型

| 項目 | 技術 | 原因 |
|---|---|---|
| Windows App | Flutter | 跨平台，未來可延伸 Android、iOS、Web、macOS |
| Backend | NestJS | 模組化，適合大型企業系統 |
| 程式語言 | TypeScript | 型別安全，較適合長期維護 |
| API | REST API | 結構清楚，容易測試與維護 |
| Database | PostgreSQL | 關聯能力強、交易穩定、可自由搬遷 |
| ORM | Prisma | 型別安全、支援 Migration、適合 NestJS |
| Storage | Storage Adapter | 可自由切換雲端、NAS、MinIO 或 S3 |
| Container | Docker | 開發、部署與未來搬遷較一致 |
| Version Control | Git + GitHub | 程式碼版本管理與備份 |

---

## 四、開發模式

採用：

> **本機開發，雲端運行**

### 你的電腦負責

- VS Code
- Claude Code
- Flutter
- NestJS 程式開發
- Git
- 本機測試

### 雲端負責

- NestJS API
- PostgreSQL 資料庫
- 文件儲存
- 使用者驗證
- LINE Webhook
- 系統通知
- 定期備份

因此，即使你的電腦關機，公司仍然可以正常使用系統。

---

## 五、雲端策略

第一階段採用雲端部署。

原因：

- 不需要先購買伺服器
- 不需要機房
- 不需要固定 IP
- 不需要自行維護硬體
- 可立即開始開發與測試
- 外勤與遠端人員可直接使用
- 公司停電時，雲端系統仍可繼續運行

開發與測試階段可先使用免費方案。

正式投入公司使用前，再評估並升級正式付費方案。

---

## 六、不被雲端服務綁定

平台不得把核心商業邏輯寫在 Supabase 專屬功能中。

Supabase 第一階段只作為：

- PostgreSQL 主機
- Authentication 基礎服務
- Storage 文件儲存
- 管理介面

所有核心商業邏輯必須放在：

```text
NestJS Backend
```

包含：

- 公司資料隔離
- 權限
- 簽核流程
- 成本計算
- 請款
- 付款
- 文件權限
- LINE 邏輯
- 模組互動
- 操作紀錄

因此，Supabase 只是目前的部署位置，不是平台核心的一部分。

---

## 七、未來搬遷策略

未來公司具備以下任一環境時：

- NAS
- 自建伺服器
- 機房
- VPS
- 其他雲端

都可以進行搬遷。

目前架構：

```text
Windows／LINE
      ↓
NestJS API（雲端）
      ↓
PostgreSQL（雲端）
      ↓
Storage（雲端）
```

未來可改為：

```text
Windows／LINE
      ↓
NestJS API（NAS 或自建伺服器）
      ↓
PostgreSQL（NAS 或自建伺服器）
      ↓
Storage（NAS）
```

搬遷時主要修改：

- API 位址
- 資料庫連線位置
- Storage 位置
- 環境變數
- DNS 或網域設定

Windows、LINE 與未來手機 App 不需要重寫。

---

## 八、可搬遷項目

| 項目 | 能否搬回 NAS | 搬遷方式 |
|---|---:|---|
| NestJS API | 可以 | Docker 容器搬遷 |
| PostgreSQL 資料庫 | 可以 | `pg_dump`／`pg_restore` |
| 公司文件 | 可以 | 批次下載、同步或 S3 相容工具 |
| 使用者帳號 | 可以 | 匯出資料與驗證設定 |
| 簽核、成本、工期資料 | 可以 | 隨 PostgreSQL 搬遷 |
| 系統設定 | 可以 | 資料庫與環境設定 |
| 操作紀錄 | 可以 | 隨資料庫搬遷 |

---

## 九、資訊安全原則

### 1. 前端不得直接連資料庫

```text
Windows／LINE
↓
NestJS API
↓
PostgreSQL
```

資料庫密碼不可放在 Windows 軟體中。

### 2. 資料庫不得直接公開

PostgreSQL 不應直接暴露於公開網路，只允許 NestJS API、指定管理來源與備份服務存取。

### 3. 所有 API 都必須重新驗證權限

每次 API 操作必須檢查：

```text
使用者身分
↓
所屬空間
↓
所屬公司
↓
模組是否啟用
↓
角色與權限
↓
是否能操作該筆資料
```

不能只依靠前端隱藏按鈕。

### 4. 公司資料隔離

所有公司業務資料都必須包含：

```text
company_id
```

任何資料查詢都必須同時檢查登入者、公司、資料 ID、模組權限與操作權限。

### 5. 密碼安全

密碼只能儲存雜湊值，不得明碼儲存。

第一階段必須具備：

- 密碼雜湊
- Access Token
- Refresh Token
- 登出失效
- 登入失敗限制
- Token 到期管理

### 6. HTTPS

所有外部連線均使用 HTTPS。

### 7. 敏感權限獨立管理

財務與敏感資料權限應細分，例如查看成本、查看毛利、建立付款、核准付款、匯出財務資料與下載機密文件。

### 8. Audit Log

重要操作必須留下稽核紀錄，包括使用者、時間、公司、模組、資料 ID、操作類型、修改前後內容、IP 或裝置資訊及操作結果。

### 9. Soft Delete

一般業務資料採軟刪除：

```text
deleted_at
deleted_by
```

只有具備特殊權限的管理程序才能永久刪除。

### 10. 金鑰與秘密管理

資料庫密碼、LINE Channel Secret、Token 簽章金鑰、Storage 金鑰及第三方 API 金鑰不得寫入程式碼，應使用環境變數或秘密管理工具。

---

## 十、文件儲存策略

PostgreSQL 只儲存文件資訊，包括文件名稱、類型、位置、大小、版本、上傳者、時間、關聯公司、關聯專案、權限與雜湊值。

實際檔案放在 Storage，所有模組透過：

```text
Storage Adapter
```

存取文件。

第一階段支援 Supabase Storage；未來可切換 NAS、MinIO、S3 相容儲存或其他雲端儲存。

---

## 十一、資料庫與 Migration

核心資料庫使用標準 PostgreSQL。

所有資料表結構變更都必須透過：

```text
Prisma Migration
```

管理，並納入 Git 版本控制。

---

## 十二、模組化單體架構

第一階段採用：

> **模組化單體（Modular Monolith）**

NestJS 專案依功能拆分：

```text
src/
├── auth/
├── users/
├── spaces/
├── companies/
├── permissions/
├── modules/
├── projects/
├── approvals/
├── schedules/
├── costs/
├── documents/
├── payment-requests/
├── payments/
├── notifications/
├── line/
└── audit/
```

所有模組放在同一個後端專案中，但程式結構彼此分離。

第一階段不使用微服務。

---

## 十三、Docker 策略

Docker 作為標準開發與部署方式，負責 NestJS API、PostgreSQL、未來 MinIO、備份工具與其他後端服務。

目的：

- 本機與正式環境一致
- 換電腦較容易
- 未來搬到 NAS 較容易
- 部署流程可重複
- 減少環境設定差異

---

## 十四、備份策略

不得只依賴 Supabase 內建備份。

至少建立三層備份：

```text
第一層：雲端平台自動備份
第二層：定期 PostgreSQL 邏輯備份
第三層：備份複製到其他位置
```

未來可採：

```text
雲端 PostgreSQL
↓ 每日備份
備份檔
↓
NAS
↓
異地備份
```

文件亦需獨立同步，且資料庫備份與文件備份必須能對應同一時間點。

---

## 十五、還原測試

正式上線前必須進行至少一次完整還原測試：

1. 建立資料庫備份
2. 建立文件備份
3. 在另一個測試環境還原 PostgreSQL
4. 還原文件
5. 啟動 NestJS API
6. 啟動 Windows 測試程式
7. 驗證登入、專案、文件、簽核與付款資料
8. 記錄還原步驟與問題

---

## 十六、未來 NAS 策略

NAS 不一定取代雲端。

優先建議採用：

```text
雲端
├── 正式 API
├── 正式資料庫
├── LINE Webhook
└── 即時服務

NAS
├── 文件備份
├── 資料庫備份
├── 歷史文件
└── 災難復原副本
```

此方式可避免公司停電、NAS 故障或雲端故障造成單點失效。

---

## 十七、完全搬回 NAS 的必要條件

若未來要將 API、Database 與 Storage 全部搬回 NAS，至少需要：

- 支援 Docker 或 Container Manager
- 足夠 CPU 與記憶體
- 建議至少 16 GB RAM，實際依使用量增加
- 適合資料庫的 SSD 或儲存配置
- UPS 不斷電系統
- 固定 IP 或安全對外入口
- 網域與 HTTPS
- 防火牆
- VPN 或 Zero Trust
- 異地備份
- 定期更新
- 資料庫監控
- 系統監控
- 完整還原測試
- 有人負責維護

NAS 不等於天然安全。

---

## 十八、第一階段暫不採用

為降低複雜度，第一階段暫不採用：

- AI
- 微服務
- Kubernetes
- Redis
- GraphQL
- Elasticsearch
- 多資料庫
- 即時多人共同編輯
- 複雜 Message Queue
- 自動擴容
- 多地區部署
- 離線同步

---

## 十九、費用策略

開發與測試期間可優先使用免費方案。

正式營運前可能產生：

- PostgreSQL 雲端費用
- API 主機費用
- 文件儲存費用
- 備份空間費用
- 網域費用
- LINE 訊息費用
- 監控服務費用
- 流量費用

任何付費服務在採用前必須列出：

- 是否必要
- 一次性費用
- 每月費用
- 依使用量費用
- 免費額度
- 免費替代方案
- 可否日後搬遷
- 停用後影響

未經確認，不採用新的付費服務。

## 二十一、第 3 步正式原則

1. Windows 使用 Flutter 開發。
2. 後端採用 NestJS 與 TypeScript。
3. API 採用 REST API。
4. 資料庫採用標準 PostgreSQL。
5. 使用 Prisma 管理 ORM 與 Migration。
6. 第一階段採用「本機開發、雲端運行」。
7. 前端不得直接連接資料庫。
8. 所有核心商業邏輯集中於 NestJS。
9. 採用 Storage Adapter，避免綁定單一儲存服務。
10. Supabase 只作為第一階段基礎設施，不作為平台核心。
11. 所有公司資料必須以 `company_id` 隔離。
12. 所有 API 必須重新驗證身分、公司、模組與資料權限。
13. 密碼只能儲存雜湊值。
14. 所有外部連線必須使用 HTTPS。
15. 重要操作必須建立 Audit Log。
16. 一般業務資料採 Soft Delete。
17. 所有金鑰與密碼使用環境變數或秘密管理工具。
18. Docker 作為標準開發與部署方式。
19. 所有資料庫結構變更透過 Migration 管理。
20. 雲端只是第一階段部署位置，不是永久綁定。
21. 平台必須支援搬遷至 NAS、自建伺服器、VPS 或其他雲端。
22. 第一期採用模組化單體，不使用微服務。
23. 正式環境必須建立多層備份。
24. 正式上線前必須完成還原測試。
25. 雲端與 NAS 都不得成為唯一備份來源。
26. 未來優先採用雲端正式運行、NAS 備份與災難復原。
27. 完全搬回 NAS 前，必須確認硬體、網路、UPS、資安與維護能力。
28. 所有付費服務須事前揭露並取得同意。
