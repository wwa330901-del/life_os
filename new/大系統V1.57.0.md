# 大系統 V1.57.0（2026-08-05）

行事曆循環事件（每天/每週/每月）+ 完整編輯範圍（只改這次／這次以後／全部）。

## 設計

一個循環事件不會真的把每一次發生都存成一筆資料庫紀錄——`CalendarEvent` 本體只存循環規則（`recurrenceFrequency`：NONE/DAILY/WEEKLY/MONTHLY，`recurrenceUntil`：選填的結束日，不填就一直重複），每次查詢某個日期範圍（App 月曆一律是這樣查）時才即時展開出這段範圍內實際有哪幾次發生（`apps/api/src/calendar/calendar-recurrence.ts`，跟平均成本股票快取一樣的「不預先算好、查詢時才算」思路，只是這裡是純日期數學，不是金額）。

- DAILY/WEEKLY 用「anchor 日期 + 間隔天數」直接算；MONTHLY 沿用 `finance-recurring-schedule.ts` 既有的「超過當月天數就夾到最後一天」邏輯（例如 1/31 循環，2 月就落在 2/28，3 月又回到 31）。
- 每次展開都會先「快轉」到查詢範圍附近再逐次往前走，不會真的從循環開始那天一天一天算到現在，避免舊事件每次查詢都要走幾千次迴圈。

「只改這次／這次以後／全部」這三種編輯範圍，實作方式跟 Google 日曆背後的真實模型一樣：

- **全部**：直接改循環本體那一列，之前的個別調整（如果有的話）不受影響。
- **只改這次**：新增一張 `CalendarEventException`，記錄「這個循環在某一天的偏差」（改掉的內容，或是 `cancelled: true` 代表這天被跳過），循環本身完全不動。
- **這次以後**：把原本的循環從這次的前一天截斷（`recurrenceUntil`），另外新建一個從這次開始的新循環事件，承接原本這次之後的所有個別調整（如果之前有對更晚的某次做過「只改這次」，那筆調整會跟著轉移到新循環底下）。

新增/編輯表單裡「只改這次」不會顯示循環頻率/結束日欄位——改一次不應該連帶動到整個循環規則。

## 範圍

- Google 行事曆同步刻意不處理循環事件——這個功能純粹是 App 內部的，循環事件永遠不會有 `googleEventId`，也不會出現在同步的推送/拉取邏輯裡。要嘛之後補 Google 那邊的 RRULE 對接，要嘛維持現狀，這次先不做（範圍太大）。
- 共用行事曆（`CalendarSharesService.combinedEvents`）也會展開循環事件——自己的跟被分享者的都一樣，`CalendarEventsService` 多拆出一個不做使用者授權檢查的 `listForSpace`，共用行事曆那邊自己負責授權（分享關係是否已接受），跟看自己行事曆的授權（`assertCalendarSpace`）分開處理。

## 修正

- Schema：`CalendarEvent` 新增 `recurrenceFrequency`/`recurrenceUntil`；新增 `CalendarEventException` 表。
- `apps/api/src/calendar/calendar-recurrence.ts`：純日期數學（不依賴 Prisma/Nest，跟 `finance-recurring-schedule.ts` 一樣可以直接單元測試），9 個測試涵蓋每天/每週/每月/月底夾算/結束日/舊事件快轉/合併展開。
- `CalendarEventsService`：`list()` 合併一般事件跟展開後的循環發生；新增 `updateOccurrence`/`removeOccurrence` 處理三種編輯範圍；新增 `POST .../events/:id/occurrence`（PATCH 實際上）與 `DELETE .../events/:id/occurrence` 兩個端點，`:id` 永遠是循環本體的 id，搭配 `occurrenceDate` + `scope`。
- App：新增/編輯行程表單多了「循環」下拉選單跟「結束於」欄位；編輯/刪除一個循環事件的某次發生時，會先跳出「只改這次／這次以後／全部」三選一，才進到編輯表單或直接刪除；月曆事件卡片有循環圖示標示。

`tsc --noEmit`、既有 + 新增共 60 個 API 單元測試全過，`flutter analyze` 乾淨。
