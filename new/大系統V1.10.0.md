## 一、這次改動的起因

V1.9.0 的「等待使用者實際測試」還沒收到回饋前，開發就先接著往下做了三輪：

1. **合約範本系統**：使用者的需求是「合約書、估價單這些文件不用每次手key，套一個範本自動把專案資料填進去」。做法定案為：範本本身是預先人工標記過 `{{欄位}}` 的 `.docx`（標記這件事需要人／AI 讀過文件找出哪些是要填的空格，不是自助上傳就能做），存進資料庫，依專案的「類型」屬性篩選出哪些範本可用，產生時用 docxtemplater 在後端做文字替換，確保排版跟原始範本一模一樣；PDF/列印則交給桌面端本機安裝的 LibreOffice 做轉檔。
2. **開工日改名 + 版面整併**：使用者測試後回饋「開工日」跟其他屬性混在一起顯示不一致，且這個日期實際上是合約簽約日、不是真的開工，所以更名「簽約日期」並跟其他屬性用同一種輸入框樣式呈現。
3. **合約完工日回寫 + 排程警示**：合約範本裡通常會有一個「完工日」欄位（例如裝修工程承攬合約書的完工日），簽了合約就等於專案有了正式的「預計結案日」。使用者要的效果是：產生合約文件時挑選的完工日，自動寫回專案的預計結案日，之後工期表算出來的完工日一旦超過這個合約完工日，要在工期表顯示警示，而不是使用者自己拿日曆對。

## 二、Prisma schema + migration

- 新增 `DocumentTemplate`（每個空間自己的文件範本）：`code`（該空間自訂的編碼，例如「JWD-3-1」）、`name`（例如「裝修工程承攬合約書」）、`category`（編碼對應的分類人讀標籤，例如「合約」，純顯示用）、`docxData`（`Bytes`，已標記好 `{{key}}` 的原始 docx）、`fields`（`Json`，`[{key, label, type?, source?, writesTo?}]`）、`allowedTypeOptionIds`（`String[]`，對應該空間「類型」屬性下的 `ProjectPropertyOption` id，決定哪些專案類型能用這份範本）。`@@unique([spaceId, code])`。
- `fields` 的欄位定義：`type` 是 `"text"`（預設）或 `"date"`；`source` 是 `null`（純手填）、`"project.name"`/`"project.startDate"`（專案自己的固定欄位）、或 `"property:<name>"`（依名稱查專案自己的 `propertyValues`）；`writesTo` 是反向——`date` 型欄位若設 `"project.endDate"`，代表產生這份文件時挑的日期要回寫到專案自己的 `projectEndDate`。
- `Project` 新增 `projectEndDate DateTime? @db.Date`（合約完工日／預計結案日，nullable，通常要等合約範本真的被填過才會有值）。
- Migration：`DocumentTemplate` 建表 + `Project.projectEndDate` 新增欄位，純 DDL，沒有既有資料要搬。

## 三、後端

- `documents/` 新模組：`DocumentTemplatesService`（平台管理員 CRUD，規則比照 project-properties——列表/建立/更新一律排除 `docxData` 這個多 KB 二進位欄位不進 metadata 回應，只有下載/填單端點才回真正的位元組）+ `ProjectDocumentsService`（專案端：`listForProject` 依專案「類型」屬性值篩出該類型允許的範本；`fill` 用 `PizZip` + `Docxtemplater`，分隔符號用 `{{` `}}`（不是套件預設的單大括號，避免跟合約內文裡本來就有的 `{`/`}` 撞在一起），把值代入後回傳 buffer）。
- `ProjectsService`/`schedule.service.ts`：`update` 支援寫入 `projectEndDate`；排程計算完工期後，如果 `projectEndDate` 有值且所有工項算出來的最晚完工日超過它，多推一筆新的 `SchedulingIssue`（`ExceedsContractDeadline`），複用既有的警示 banner／列高亮 UI，不用另外做一套顯示邏輯。
- 全部單元/整合測試維持 43 個全過（`npm test`）。

## 四、前端

- 新模型 `document_template.dart`（`DocumentTemplate`/`DocumentField`/`DocumentFieldType`）、新 provider `document_templates_provider.dart`（`projectDocumentTemplatesProvider(projectId)`、空間端管理用的 provider）。
- 專案詳細頁新增「相關文件」分頁（`project_documents_tab.dart`）：列出該專案類型可用的範本，「產生文件」開一個對話框，依範本的 `fields` 動態長出文字框／日期選擇器（`source` 對得上的欄位自動帶入專案既有資料，其餘留白手填），送出後呼叫後端 `fill`，接著跑 `_writeBackDates`（凡是 `writesTo == "project.endDate"` 的日期欄位，把選到的日期呼叫 `updateProject` 寫回專案），最後讓使用者選「另存 Word」（永遠可用，位元組跟範本一致）／「另存 PDF」／「列印」（後兩者透過 `DocumentFillService` 呼叫本機 LibreOffice `soffice.exe` 轉檔，抓不到 LibreOffice 就跳提示要求先安裝）。
- 空間層級「專案設定」畫面（原「屬性設定」，這輪改名並收緊權限——現在只有平台管理員看得到，理由是這個畫面會影響空間裡每一個專案，不該讓一般空間 OWNER/ADMIN 自己改）新增「文件選用」區塊：每份文件範本可以勾選要開放給哪些「類型」的專案使用（沒有「類型」單選屬性的空間會提示無法設定）。
- 「專案資料」分頁：日期型欄位（`projectStartDate` 這個固定欄位，以及任何通用 `DATE` 屬性）改成跟文字/單選欄位同一種有框線、有標籤的輸入樣式，不再是「純文字＋按鈕」的不一致版面；`projectStartDate` 顯示名稱從「開工日」改成「簽約日期」，視覺上併入其他屬性同一份清單裡（後端欄位、排程引擎的錨點都沒變，純顯示層調整）。
- `Project` model 新增 `projectEndDate`。

## 五、驗證方式與限制

後端：`npm test`（43 個測試全過）。前端：`flutter analyze` 乾淨（僅 9 個 `use_null_aware_elements` 風格提示，非錯誤）、`flutter build windows --release` 成功。**這輪的合約範本上傳/標記、文件產生對話框、PDF/列印轉檔、排程超期警示這幾個互動流程都還沒有真人實際點過一輪**，下次要請使用者實際測試——尤其是 LibreOffice 轉檔在使用者自己機器上是否找得到安裝路徑。目前範本的「上傳/標記」還沒有自助上傳 UI，是後端直接寫入資料庫的方式做（見 `DocumentTemplatesService` 註解）——之後若要開放使用者自己上傳範本再標記欄位，需要額外的一輪設計。
