---

## 一、這次改動的起因

使用者原本的請求還包含幾個小項（類型/狀態各設定 3 個選項、專案卡片顯示類型/狀態/案名/PM、工期表欄位各自可調寬），但最後一項是重點：「專案資料表是一個系統，所以平台管理員可以針對這個系統有一個設定區，可以自行設定要有什麼屬性，就像 notion 的資料庫屬性一樣」。追問後確認三件事：

1. 現有 5 個欄位（類型/狀態/業主名稱/專案地點/案號）**全部併入**新系統，不是保留舊欄位再疊加新的——「境為」空間目前的設定，變成「境為」自己的屬性定義
2. 這次支援 4 種型態：**文字、單選（下拉）、數字、日期**（多選/核取方塊之後再加）
3. 屬性是**每個空間各自設定**，不是像類型/狀態一樣全平台共用一份——跟使用者原本以為的「平台管理員設定」不同，這是本輪釐清後的修正方向

**分兩階段做**：階段一（這次）新增通用屬性系統，把「境為」現有 5 個屬性原封不動搬進去，舊的 `typeId`/`statusId`/`clientName`/`siteAddress`/`caseNumber` 欄位保留在資料庫但前端不再讀寫（安全網）；階段二（之後使用者用過一輪確認沒問題再做）才正式清掉舊欄位跟舊的平台管理後台類型/狀態畫面。

## 二、Prisma schema + migration

新增 `ProjectPropertyDefinition`（每個空間自己的屬性定義：name/type/sortOrder）、`ProjectPropertyOption`（SELECT 屬性的選項）、`ProjectPropertyValue`（一個 project × 一個 definition 一筆，`textValue`/`numberValue`/`dateValue`/`optionId` 四個 nullable 欄位依 `definition.type` 只填一個——單表多型的務實 EAV 做法，不是真正的多型子表）。

Migration 分兩支：`add_project_property_system`（純 DDL 建表）+ `migrate_project_properties_data`（PL/pgSQL DO block：對每個有專案的 space 建立 5 筆定義、把 `ProjectTypeOption`/`ProjectStatusOption` 的選項複製成該 space 專屬的 `ProjectPropertyOption`、把每個專案現有的欄位值搬成對應的 `ProjectPropertyValue`）。本機 Docker Postgres 驗證過搬遷後筆數對得起來、舊欄位資料沒被動到。另外把舊欄位全部改 nullable（`loosen_old_project_fields_to_nullable`），純粹當安全網。

## 三、後端

- 新增 `project-properties.controller.ts`/`.service.ts`（掛在 `spaces/:spaceId/properties`）：屬性定義的 CRUD + SELECT 屬性選項的 CRUD，管理權限是**該空間自己的 OWNER/ADMIN**（`MembershipRole`），不是平台管理員——這跟類型/狀態選項用 `PlatformAdminGuard` 不同，是這次的核心差異
- `CreateProjectDto`/`UpdateProjectDto` 拿掉寫死的欄位，改成 `propertyValues: {definitionId, value}[]`，服務層依 definition 的 type 分派到對的欄位並做型別驗證（數字/日期格式錯、SELECT 選項不存在都會擋下）
- `ProjectsService.create`/`update` 包進 `$transaction`，屬性值驗證失敗不會留下半成品專案
- 全部用本機 Docker Postgres + curl 實測過：空間 OWNER 能新增/刪除屬性、一般 MEMBER 不能、建立專案帶新格式的 propertyValues、驗證失敗會整筆回滾

## 四、前端

- 新模型 `project_property.dart`：`PropertyType`/`PropertyOption`/`PropertyDefinition`/`ProjectPropertyValue`（含 `displayValue` 依型態組出可讀字串）
- 新 provider `project_properties_provider.dart`：`spacePropertiesProvider(spaceId)`
- `Project` model 拿掉 `clientName`/`siteAddress`/`type`/`status`/`caseNumber`，改成 `propertyValues: List<ProjectPropertyValue>`，加 `propertyByName`/`propertyValue` 兩個查找 helper
- 新增專案對話框（`create_project_dialog.dart`）整個重寫成動態表單：依空間的屬性定義動態長出對應輸入元件；專案名稱自動組成改成**依名稱比對**（找得到「業主名稱」「專案地點」兩個文字屬性 + 「類型」單選屬性才自動組，找不到就不自動帶，優雅降級）
- 「專案資料」分頁（`project_info_tab.dart`）改成迴圈渲染該空間目前定義的每個屬性
- 新增空間層級「屬性設定」畫面（`space_properties_screen.dart`），側欄齒輪圖示入口，只有該空間 OWNER/ADMIN 看得到；`AppSidebar` 依 `space.role` 判斷是否顯示
- 專案清單卡片徽章改成依名稱在 `propertyValues` 裡找「類型」「狀態」，找不到就不顯示

## 五、驗證方式與限制

後端：`npm test`（43 個測試全過）+ 本機 Docker Postgres 驗證 migration 搬遷正確性 + curl 實測權限與資料驗證。前端：`flutter analyze` 全程乾淨、`flutter build windows --release` 成功、啟動後截圖確認沒有崩潰。這台機器滑鼠自動化不可靠，**動態表單、屬性設定畫面這些互動還沒有真人點過一輪**，下次要請使用者實際測試。
