## 一、定期交易：日期選擇器＋遇假日提前/延後（App 版本 v1.0.0）

**設計決定**：使用者原話「記帳系統的定期交易日期不要用每月第幾天，改用日期。並且遇到假日可以選擇提前或延後」。確認過三件事：
1. 「改用日期」是指 App 端的**輸入介面**從文字框「每月第幾天（1-31）」改成真正的日期選擇器（`showDatePicker`），使用者用日曆點一天——資料庫底層還是儲存 `dayOfMonth`（每月同一天重複觸發），這只是 UX 改良，不是規則改變。
2. 假日範圍：週末 **+** 台灣國定假日（沿用工期表排程已經有的 `isTaiwanHoliday` 假日表，只涵蓋 2026-2027）。
3. 提前/延後是**新增/編輯這筆定期交易時設定一次**（不是每次觸發都問），選項：不調整／提前到平日／延後到平日。

**後端改動**：
- `FinanceRecurringTransaction` 新增 `holidayAdjustment FinanceRecurringHolidayAdjustment @default(NONE)` 欄位（新 enum：`NONE`/`EARLIER`/`LATER`）。
- 純日期運算抽成 `apps/api/src/finance/finance-recurring-schedule.ts` 的 `effectiveTriggerDate(year, month, dayOfMonth, lastDayOfMonth, adjustment)`——刻意不 import 任何 Prisma/Nest 型別，因為當時發現：**在 jest spec 裡 import 生成的 Prisma client（`generated/prisma/client.js`）會解析失敗**（ts-jest 跟不上 NodeNext 的 `.js`→`.ts` remap），所以凡是要幫 finance/stocks 這類 module 寫單元測試，都要避開這條 import 鏈，把純邏輯抽到獨立檔案、用字串聯集型別代替 Prisma enum（例如 `type Adjustment = 'NONE' | 'EARLIER' | 'LATER'`，結構上跟 Prisma 生成的物件字面聯集相容，可以直接互傳不用轉型）。
- 每日 cron（`FinanceRecurringTransactionsService.processDueRecurringTransactions`）改成算出 `effectiveTriggerDate` 後跟今天比對，不再直接比對 `dayOfMonth`。

**App 端改動**：`finance_recurring_tab.dart` 的日期輸入框換成 `showDatePicker` + `InputDecorator`，新增「遇假日」下拉選單。

**發布**：`v1.0.0`（使用者當時明確要求下一次更新直接跳版號到 1.0.0，不再延續 0.21.x）。

## 二、AI／投資／簽核三合一提案，逐項確認後的結果

### 2.1 AI 整合 — 暫停，但設計已經談定

多輪確認後定案（**還沒動工，之後接續時直接照這個設計走，不用重談**）：
- 供應商：**Anthropic Claude**（不是 OpenAI）——使用者原話是「把你自己加進去」，兩邊註冊/計費成本差不多，選 Claude 才是真的把「自己」加進去。
- 模型：**`claude-sonnet-5`**（性價比最好，使用者在 Sonnet 5 跟 Opus 5 之間選了前者）。
- 入口：**App 內建對話畫面 + LINE 自由文字**都要（使用者選「兩邊都要，工作量最大」那個選項）。
- 模式：**問答制**（使用者問才答），不做主動推播式的分析摘要。
- 資料範圍：**全部開放**——記帳、代辦事項（含專案代辦）、專案進度（工期表）、行事曆，個人空間全部 + 有權限的公司空間專案。
- App 端對話記憶：只在這次開啟畫面期間有效，不做永久儲存。
- 需要 `ANTHROPIC_API_KEY`（使用者還沒申請，需要去 console.anthropic.com 註冊+綁卡）。

同時做了一份 `docs/AI服務費用分析.md`，寫清楚 Claude API 的計費原理（token 計價、無月費、儲值扣款）跟「單一個人用量」的每月花費預估（美金+新台幣，假設 1 美元≈31.5 台幣）。**這份文件的預估數字是照上面這個設計算的，之後如果設計有變，要記得回來更新，不要照舊數字報價。**

## 三、投資股票系統落地（App 版本 v1.1.0）

台股專用，只做「記錄＋提醒＋統計」，不含 AI 買賣建議（見上）。個人空間新增「投資」模組，跟「記帳」平行（`DashboardView` 現在最上層是「記帳／投資」的 TabBar，不再直接塞 `FinanceHomeScreen`）。

### 3.1 手動買賣（`StockTransaction`）— T+2 交割

使用者原話確認過的規則：
- 輸入欄位：**股票代碼＋成交價（每股）＋成交成本（總金額）＋帳戶**，股數 = 成交成本 ÷ 成交價，系統自動算，使用者不用自己乘。（一開始有來回調整過一次：曾經想過「只填總金額，用當天股價自動推算股數」，後來使用者又改回「要自己填成交價」，跟定期定額統一格式。）
- **交割時間跟真實股市一樣**：登記買賣當下不會馬上扣款/入帳，要等 **T+2**（成交日後第 2 個交易日，跳過週末跟台灣國定假日）才實際動錢。T+2 計算沿用工期表排程同一套「工作日」引擎，寫在 `apps/api/src/stocks/stock-settlement-schedule.ts` 的 `computeSettlementDate`（純函式，有獨立 jest spec）。
- 交割當天由每日 cron（`StocksSettlementService.settleDueTransactions`，早上 9 點 Asia/Taipei）自動在對應帳戶建立真正的記帳交易（買=支出、賣=收入），並把 `settled` 標記為 true。**已交割的交易不能刪除**（金錢已經真的動了，刪股票交易不會連動刪掉記帳交易，會造成兩邊對不起來）。
- 使用者額外要求：**交割前一天，如果帳戶餘額不夠付交割款，要用 LINE 提醒**。落地成 `StocksSettlementService.warnIfInsufficientForTomorrow`，晚上 8 點 Asia/Taipei 跑，把明天到期的買入交易依帳戶加總，跟該帳戶目前算出來的餘額比較，不夠就推播。

### 3.2 定期定額（`StockRecurringInvestment`，DCA）

跟定期交易共用「每月第幾天＋遇假日調整」的設計（同一個 `FinanceRecurringHolidayAdjustment` enum、同一個 `effectiveTriggerDate` 函式）。因為 DCA 每次成交金額都不一樣，**到期不會自動記一筆，只發 LINE 提醒**，並把 `awaitingReply` 標記成 true。使用者回覆「股票代碼 成交價 投入成本」（例如「0050 600 20000」，跟手動買賣同一套算股數邏輯）後，`StocksRecurringService.fulfillPendingReply` 才真正記一筆股票交易（也會照樣走 T+2 交割）。

這個設計連帶決定了 LINE 指令的格式：**手動買賣一定要有「買股」/「賣股」開頭**，因為 DCA 回覆是純數字（代碼＋成交價＋投入成本，沒有關鍵字）——如果手動買賣也允許純數字，兩者會分不清楚。

### 3.3 股價（`StockPriceCache`，全站共用，不分空間）

使用者確認：「開盤的時候一直拉盤中，收盤的時候拉一次官方的」。落地成兩支 cron（`StocksPriceService`）：
- **每日收盤**（14:30 Asia/Taipei，平日）：打證交所**官方免費** OpenAPI（`openapi.twse.com.tw/v1/exchangeReport/STOCK_DAY_ALL`，不用金鑰，回全市場清單再篩出有追蹤的代碼）——穩定、有文件規格。
- **開盤時段**（每 5 分鐘，09:00-13:30 Asia/Taipei，平日）：打證交所**非官方**的即時報價介面（`mis.twse.com.tw/stock/api/getStockInfo.jsp`）——這條沒有正式文件、格式說變就變，包在 try/catch 裡，拉不到就維持上次的值（畫面自動退回顯示收盤價），不會讓整支排程掛掉。**這是使用者知情後的取捨**（有明確告知非官方介面的風險，使用者選擇兩個都要）。

追蹤範圍只包含「目前有交易紀錄或有效定期定額計畫的股票代碼」，不會對整個台股清單發請求。

### 3.4 持股統計（`StocksHoldingsService`）

用**移動平均成本法**：每筆買入把股數跟成本一起累加；每筆賣出扣掉股數，同時按比例扣掉一部分成本基礎（不是用當次賣出價格去算損益，是用平均成本）。目前市值 = 股數 × 快取的最新報價（即時價優先，沒有就用收盤價，兩個都沒有就顯示「無報價」）。**沒有做逐筆成本（FIFO/LIFO）**，是刻意簡化，使用者沒要求就不要自己加。**沒有算手續費/證交稅**，同樣沒要求就不做。

### 3.5 LINE 新增指令 + 選單擴充

新增「買股」「賣股」「持股總覽」三個指令（`LineService` 的 `tryStockCommand`/`tryStockDcaReply`/`sendStockHoldings`）。連帶把靜態 LINE 選單從 4 顆按鈕擴充成 **6 顆**（記帳/財務總覽/代辦事項/代辦事項總覽/股票買賣/持股總覽，2500×843、2列×3欄）。

**LINE 選單重畫的技術細節，以後還會用到**：選單本質上是一張圖片，按鈕文字是畫進圖片裡的像素，不是 LINE 動態顯示的文字——按鈕數量一變，一定要重新出圖再上傳，沒有例外。這次用 PowerShell + `System.Drawing`（本機 Windows 才有中文字型，字型用 `Microsoft JhengHei`）畫圖，再用 Node 呼叫 LINE 的 `richmenu` REST API（list 舊選單→刪除→建立新選單定義→上傳圖片→設成所有使用者的預設選單）。Channel access token 使用者當下貼給 Claude Code，只在該次執行用環境變數帶入，**沒有存進任何檔案或 git**，腳本跟產生的圖片用完就刪，不留在專案裡。

### 3.6 資料庫

新增 `StockTransaction`、`StockRecurringInvestment`、`StockPriceCache` 三張表，`FinanceAccount`/`Space` 補上對應的反向關聯。Migration：`20260801100000_stock_investment_system`。
