## 一、真正解決卡頓

使用者回報「工期表用起來還是很卡頓，每做一個動作都需要過好幾秒」——V1.6.0 把 3 個依序 GET 改成平行送出，但沒有解決根本問題：**這 3 個 API 各自獨立重新檢查一次「這個人是不是這個空間/專案的成員」**，每次檢查都是好幾次循序的資料庫查詢（`getProjectOrThrow` → `getForUserOrThrow` → `companyMembership.findUnique`），平行送出並沒有減少「每個請求各自要付出的認證延遲」。

修法：新增 `GET /projects/:id/editor-state`（`schedule.service.ts` 的 `getEditorState`），一次請求回傳 `{project, items, schedule}`，只做一次權限檢查。前端 `ProjectEditorNotifier._fetch()` 改成呼叫這一個端點，取代原本平行送出的三個。用 curl 直接測過部署好的 API（`https://life-os-api-yhh2.onrender.com`），確認暖機後單一端點回應在 100-200ms 內。

## 二、公司空間導覽簡化

使用者回報：「境為空間點進去之後就應該看到每一個專案了，不需要再點專案管理」。目前只有一個真正的功能模組（專案管理），中間的「儀表板」點擊變成多餘的一步。`SpaceShell`／`AppSidebar`／`DashboardView` 都簡化：公司空間直接顯示專案清單，個人空間維持原本的「尚未推出」佔位畫面。麵包屑也拿掉了多餘的「專案管理」那一段。以後如果真的加了第二個模組，可以再把儀表板加回來。

## 三、專案成員（存取控制，不只是 UI）

使用者要求：專案成員分頁要能真的選擇成員；**只有專案成員才能看到這個專案**；新增專案的人預設是 PM。這不只是補一個分頁，而是收緊了整個 API 的存取控制——`ProjectsService.assertAccess()` 是所有專案相關端點（work-items、schedule、calendar）共用的同一個守門函式。

**規則**（已跟使用者確認）：
- 空間 OWNER/ADMIN 永遠看得到空間內所有專案，不受成員名單限制
- 一般空間 MEMBER 只看得到自己被加進去的專案
- 新增專案的人自動成為該專案 PM
- 管理成員（新增/移除/改角色）只有 PM 或空間 OWNER/ADMIN 能做，且不能移除/降級最後一位 PM

**Migration 回填**：舊專案（上線前就存在的）自動把當時空間的所有成員都加進去（空間 OWNER → PM，其餘 → 一般成員），確保沒有人因為這次改動突然看不到原本看得到的專案。Migration 檔在 `apps/api/prisma/migrations/20260725103809_add_project_members/migration.sql`，本機用 Docker 起了一份本地 Postgres（`docker-compose.yml`）驗證過 schema + 回填邏輯，並用手動產生的 JWT 對三種身份（空間 OWNER ×2、一般空間 MEMBER）curl 實測過：MEMBER 沒加入專案時列表是空的、直接打 API 拿 403；OWNER 不管有沒有加入都看得到；新增/改角色/刪除都正確限制在 PM/OWNER/ADMIN；刪除/降級最後一位 PM 會被擋下來。

新端點：`GET /spaces/:id/members`（給任何空間成員用，不只平台管理員）、`GET/POST/PATCH/DELETE /projects/:id/members`。

## 四、下一步（使用者已提出，尚未動工）

使用者接著提出：**每個專案要有「類型」「狀態」下拉選單，選項由平台管理者設定（像 Notion 資料庫那樣）**。這是下一個要做的功能，性質上跟這次的專案成員一樣是「新 schema + 新後端端點 + 新前端 UI」，會需要：
- 平台管理後台新增「管理專案類型/狀態選項」的畫面（新增/刪除/重新排序選項，可能還要顏色，像 Notion 的 tag）
- `Project` model 加 `type`/`status` 欄位（關聯到管理者定義的選項，而不是寫死的 enum）
- 專案清單/詳情頁的下拉選單 UI

**還沒進 plan mode 規劃**，下次「我要寫大系統」時如果使用者還想做這個，先確認：這些選項是「全平台共用一套」還是「每個空間可以自訂一套」（使用者說「平台管理者設定」，聽起來是全平台共用，但沒有明確排除空間自訂的可能）。
