## 一、這次改動的起因

延續 V1.11.0 之後，使用者陸續回報跟提出新需求，大致照時間順序：

1. 工期表編輯每個動作都要等好幾秒才有反應 → 追出是「寫入 + 重新整包抓取」兩次網路來回、且各自都重複做權限檢查查詢，改成單一回應解決。
2. 「文件部分我希望編輯完成之後他就是在軟體內的一個頁面了」→ 從一次性下載改成持久化記錄（`GeneratedDocument`），為未來的公司簽核系統鋪路。
3. 「合約設定開工日及完工日後自動產生工期」→ 合約填寫表單裡開工日/完工日都選了就自動算工期天數。
4. 「產生的文件要能在軟體裡預覽」→ 用 `printing` 套件的 `PdfPreview` 加本機 LibreOffice 轉檔做到。
5. 「接下來要做個人功能，第一個先用記帳系統」→ 使用者選擇「一次做完整」：分類管理、多帳戶、月度統計圖表、預算設定，分類要能自訂。
6. 記帳系統上線後使用者實際測試回饋三個問題：帳戶是否跨帳號共用（確認是個人獨立）、超預算有沒有警告（原本只有被動進度條，改成新增交易當下主動跳警告）、信用卡消費怎麼算（沿用一般帳戶邏輯，負餘額顯示「欠款」更好懂）。
7. 「我現在要用 line 輸入消費或收入然後連結到軟體自動記帳」→ 引導使用者申請 LINE 官方帳號 + Messaging API channel，做了完整的 LINE 記帳整合（webhook、帳號綁定、交易寫入）。
8. LINE 記帳上線後使用者發現「分類會變成備註」→ 追加「引導式選單流程」（支出/收入 → 分類 → 帳戶 → 輸入金額），讓 LINE 記帳的交易也能正確帶分類。
9. 使用者回報記帳金額顯示沒有千分位逗點 → 全部金額顯示（含 LINE 機器人回覆文字）補上千分位格式。
10. 使用者截圖回報文件預覽跳出「找不到 LibreOffice」→ 確認是本機環境沒裝 LibreOffice，不是程式 bug，引導使用者自行安裝。

## 二、工期表編輯延遲修正

**根本原因**：`ProjectEditorNotifier` 的每個編輯方法（`renameWorkItem`/`changeDuration`/`changeStartDate`/...）都是「呼叫 mutate API → 再呼叫 `refresh()` 整包重抓」兩次序列 HTTP 來回；後端這兩個端點（`work-items` PATCH 跟 `editor-state` GET）各自都要重新做一次「查專案 → 查空間成員權限」的存取檢查，等於每個編輯動作要跑 8-12 趟循序資料庫查詢才有畫面反應。

**修法**：
- 後端 `ScheduleService` 拆出 `buildEditorState(project)`（吃已經查好的 `project`，不重新做存取檢查），`WorkItemsService` 的 `create`/`update`/`remove`/`reorder` 改成內部呼叫這個方法，直接把「寫入後最新的 project+items+schedule」包在同一個回應裡回傳，而不是只回傳被改的那一筆 row。
- 前端 `api_client.dart` 的 `createWorkItem`/`updateWorkItem`/`deleteWorkItem`/`reorderWorkItem` 回傳型別改成跟 `getProjectEditorState` 一樣的 record（`{project, items, schedule}`，`createWorkItem` 多一個 `createdId`），`ProjectEditorNotifier` 直接把這個回應套進 `state`，不再另外呼叫 `refresh()`。

一個 mutate 動作從「2 次 HTTP + 各自的存取檢查」變成「1 次 HTTP」。

## 三、文件持久化（GeneratedDocument）

**新 Prisma model**：`GeneratedDocument`（`spaceId`/`projectId`/`templateId`(nullable, `onDelete: SetNull`)/`name`/`values Json`/`docxData Bytes`/`createdAt`/`createdByUserId`）。填範本這件事從「渲染完直接串流下載」改成「渲染完先存一筆記錄，回傳 metadata」，下載/列印/預覽都改成對這筆記錄的動作。

**後端**：`ProjectDocumentsController`（`fill` 改成建立+回傳 metadata）+ 新的 `GeneratedDocumentsController`（`GET /projects/:id/documents` 列表、`GET .../:id/download` 串流、`DELETE .../:id`）。

**前端**：`project_documents_tab.dart` 拆兩區——「可用範本」（原本的產生文件）跟「已產生的文件」（新列表，每筆有預覽/另存 Word/另存 PDF/列印/刪除）。預覽用 `printing` 套件的 `PdfPreview` widget，資料來源是既有的 `DocumentFillService.convertDocxToPdf`（本機 LibreOffice 轉檔——這也是後來「找不到 LibreOffice」那次截圖回報的根源，本機沒裝就會這樣，不是 bug）。

**合約表單自動算工期**：`DocumentField` 新增 `durationFromKey`/`durationToKey` 宣告，`_FillDialog` 偵測到兩個日期欄位都選了就自動計算天數帶入「工期(天)」欄位（仍可手動覆蓋）。JWD-3-1 範本的 `fields` JSON 已經更新（透過正式環境連線字串直接 UPDATE，不是走 migration）。

## 四、記帳系統（第一個個人功能模組）

掛在個人空間下（`SpaceType.PERSONAL`），取代原本「功能尚未推出」的 `DashboardView` 佔位畫面。

**新 Prisma models**（都掛 `spaceId`，透過 `FinanceAccessService.assertPersonalSpace` 確保只有空間擁有者能存取）：
- `FinanceAccount`（現金/銀行/信用卡/其他，`initialBalance`，餘額是動態算出來的：`initialBalance + Σ(收入-支出±轉帳)`，不落地存）
- `FinanceCategory`（收入/支出，每個空間自己的，第一次打開記帳頁時會自動 lazy seed 一組常用分類：餐飲/交通/購物/娛樂/居住/醫療/其他支出/薪資/其他收入）
- `FinanceTransaction`（收入/支出/轉帳三種 type；轉帳用 `toAccountId` 表示目標帳戶，不佔分類欄位）
- `FinanceBudget`（每分類一筆，`monthlyAmount` 是「每月固定預算」，不綁定特定月份，每次查某個月都拿當月實際支出比對）

**後端**：`FinanceModule`（4 個 controller/service：accounts/categories/transactions/budgets），路由掛在 `spaces/:spaceId/finance/...`。`FinanceTransactionsService.monthlySummary` 算月度收支分類統計，`FinanceBudgetsService.monthlyStatus` 算預算 vs 實際。

**前端**：`FinanceHomeScreen`（TabBar 五分頁：總覽/交易/帳戶/分類/預算），`fl_chart` 套件畫支出分類圓餅圖。新增交易若讓某分類超出當月預算會主動跳 SnackBar 警告（不只是總覽頁被動變紅）。信用卡負餘額顯示成「欠款 X」。所有金額顯示都用共用的 `formatAmount()`（`lib/ui/screens/finance/widgets/finance_format.dart`）加千分位逗點，輸入框本身維持純數字方便打字。

## 五、LINE 記帳整合

**目標**：使用者傳 LINE 訊息，機器人自動幫快記帳。

**帳號綁定**（新 model `LineAccountLink`，1:1 對應 `User`）：使用者在 App 記帳總覽頁按「連結 LINE 記帳」產生一次性 6 位數綁定碼（10 分鐘有效），傳給 LINE 官方帳號完成綁定——**單純加好友或裝軟體不會自動連線**，一定要走這個綁定碼交換才會把某個 LINE 帳號對應到某個 life_os 使用者。

**Webhook**（`POST /line/webhook`，`main.ts` 開啟 `rawBody: true` 才能算 HMAC 簽章）：驗證 `x-line-signature`（用 `LINE_CHANNEL_SECRET` 算 HMAC-SHA256 比對），確認是真的來自 LINE 才處理事件。

**兩種記帳方式**：
1. **一行指令**（快，但不分類）：「支出 120 午餐 現金」→ 直接解析 type/amount/note/[帳戶]，落地為 `categoryId: null`（未分類）。
2. **引導式選單**（有分類）：傳任何一句話 → 機器人用 LINE 的 Quick Reply 按鈕依序問「支出/收入」→「選分類」→「選帳戶」→ 使用者輸入金額（可加備註）完成。進行中的選擇存在 `LineAccountLink.pendingDraft`（`Json?` 欄位，`{type, categoryId, accountId}`），每個按鈕的 postback `data` 是 `t:EXPENSE`/`c:<categoryId>`/`a:<accountId>`/`cancel` 這種簡短編碼。

這是使用者實際用過一行指令方式、發現「分類變成備註」之後才追加的——**設計上就是取捨**：想快就用一行指令（不分類），想準確就用引導式選單（會多幾次來回）。

## 六、其他細節

- **DTO 補充**：`FillDocumentDto` 加 `name?`（可選的自訂顯示名稱）。
- **`fill()` 回傳型別變更**是 breaking change，但因為只有這個 App 自己在呼叫這組 API，直接改掉沒有相容性負擔。
- **Prisma `Bytes` 欄位**寫入時要包一層 `new Uint8Array(buffer)`，直接塞 Node `Buffer` 會因為 `ArrayBufferLike` vs `ArrayBuffer` 型別不相容編譯失敗（`document-templates.service.ts`/`project-documents.service.ts`/都踩過同一個坑，已經是固定寫法）。
- **Prisma `Json?` 欄位設回 `null`** 要用 `Prisma.DbNull`，不能直接塞 JS 的 `null`（TypeScript 會擋，因為要區分「這欄真的是 SQL NULL」跟「JSON 值本身是 null」）。

## 七、發布流程（沿用，Windows 部分務必照做）

1. commit + push 程式碼
2. 版本號同步改 `apps/windows_app/pubspec.yaml` 與 `apps/windows_app/installer/life_os.iss`
3. `rm -rf apps/windows_app/build/windows`（一定要做，見零、給未來的我）
4. `flutter build windows --release`
5. 確認版本號：`(Get-Item apps\windows_app\build\windows\x64\runner\Release\life_os_app.exe).VersionInfo.FileVersion` 必須等於 pubspec 版本
6. `"C:\Users\chen6\AppData\Local\Programs\Inno Setup 6\ISCC.exe" installer\life_os.iss`
7. `gh release create vX.Y.Z installer/Output/life_os_setup.exe --title vX.Y.Z --notes "..."`

**資料庫 migration**：本機沒有 Docker，改用 `npx prisma migrate diff --from-config-datasource prisma.config.ts --to-schema prisma/schema.prisma --script`（帶正式環境 `DATABASE_URL`）自動產生跟 Prisma 官方一致的 migration SQL，比手寫可靠，寫進 `prisma/migrations/<timestamp>_xxx/migration.sql` 後用 `npx prisma migrate deploy` 直接套用到正式環境驗證。正式環境連線字串是 Supabase Session Pooler，格式 `postgresql://postgres.<project-ref>:<密碼>@aws-0-<region>.pooler.supabase.com:5432/postgres`，Prisma v7 起一定要搭配 `@prisma/adapter-pg` 當 driver adapter，不能只給 `DATABASE_URL` 環境變數。

**LINE 相關環境變數**（設在 Render 的 `life-os-api` 服務）：`LINE_CHANNEL_SECRET`、`LINE_CHANNEL_ACCESS_TOKEN`，都是使用者從 LINE Developers Console 拿的，不寫進程式碼或 git。
