## 二、LINE 記帳改用底部選單切換

**核心機制**：LINE 允許把一個「Rich Menu」連結到特定某一個使用者（`POST /v2/bot/user/{userId}/richmenu/{richMenuId}`），覆蓋掉頻道預設選單，直到明確解除連結（`DELETE /v2/bot/user/{userId}/richmenu`）為止。新增 `LineRichMenuService`（`apps/api/src/line/line-rich-menu.service.ts`）：

- `getOrCreateTypeMenu()`：支出/收入/取消，固定內容、所有使用者共用，第一次呼叫時建立並在記憶體快取 id（用名稱查詢避免重啟後重複建立）。
- `createSelectionMenu(items, name)`：依項目數量動態排版（≤5 個用單排、跟主選單一樣的高度；更多則用最多 5 欄 4 列的格狀排版，符合 LINE 選單最多 20 個可點區域、最高 1686px 的限制），用 `sharp` 把 SVG 光柵化成 PNG 上傳，回傳新選單 id。分類/帳戶選單就是這樣依使用者的實際分類/帳戶動態產生的。
- `linkToUser`/`unlinkUser`/`deleteMenu`：包裝對應的 LINE API。

**流程**（`LineService`）：點主選單「記帳」→ 連到「支出/收入」選單 → 點了之後動態產生「分類」選單並連過去 → 點分類後動態產生「帳戶」選單並連過去 → 點帳戶後刪掉暫時選單、連回預設選單、回覆「請輸入金額」→ 使用者只打金額就完成。

`LineAccountLink` 新增 `pendingRichMenuId` 欄位追蹤目前連結的「暫時」選單（分類/帳戶這兩層，因為是動態產生、只服務單次流程），跟靜態共用的「支出/收入」選單分開處理——共用選單不會被刪除，暫時選單每次進下一階段前會先刪掉上一個，避免累積孤兒選單。

**中途離開流程的邊界處理**：如果使用者選單卡在「分類」階段，卻改傳「總覽」「代辦事項」「新增 XXX」之類的其他指令，`abandonFinanceFlowIfActive` 會在處理那個指令前，先把選單復原成預設、清空記帳草稿，不會卡住。

## 三、行事曆空間

**新空間類型**：`SpaceType.CALENDAR`，1:1 對應使用者（`Space.calendarOwnerUserId`，獨立於 `ownerUserId`——一個使用者可以同時有個人空間跟行事曆空間，兩者是不同欄位，不會互相排擠），跟個人空間一樣「用到才建立」（不是註冊時自動產生），在空間選擇畫面按「新增行事曆」建立。

**新 Prisma model**：
```prisma
model CalendarEvent {
  id, spaceId, title, location?, notes?, startAt, endAt?, allDay,
  googleEventId?  // null = 還沒同步到 Google，或這個空間沒連 Google
  @@unique([spaceId, googleEventId])
}
```

跟 `ProjectTodo`故意不共用/不自動連動——行事曆是行事曆、代辦事項是代辦事項，這版沒有做「代辦事項自動變成行事曆事件」這種雙向資料綁定，維持兩個獨立系統（範圍守住，避免資料模型糾纏）。

**後端**：`CalendarEventsController`（`spaces/:spaceId/calendar/events` CRUD）、`CalendarAccessService`（比照 `FinanceAccessService` 的模式，限定只有這個行事曆空間的擁有者能存取）。新增/修改事件時推送到 Google **不等待**（fire-and-forget，寫進 log 但不擋住 API 回應）——這是特意的設計，這個 app 已經踩過一次「每個編輯動作都要等網路來回」的效能坑（V1.12.0 的工期表延遲問題），這次直接避開同樣的錯誤。

**前端**：`CalendarScreen`（`table_calendar` 套件畫月曆格狀檢視），左邊月曆、右邊選中日期的議程清單（新增/編輯/刪除），頁首有「連結 Google 行事曆」按鈕跟同步狀態。

## 四、Google 行事曆雙向同步

**授權**：延伸既有的 Google 登入用 OAuth（`GoogleOAuthService`，桌面版走「開系統瀏覽器 + 本機 loopback server 接收 redirect」的 RFC 8252 流程）——新增 `connectCalendar()`，跟原本純登入用的 `signIn()` 差別在於多帶 `access_type=offline`、`prompt=consent`（強制每次都真的拿到 refresh token，不然 Google 只有使用者「第一次」同意某個 scope 時才會給）跟行事曆的 scope。這個授權是**行事曆空間專屬**的「漸進式授權」（incremental consent），不是每次登入都跟使用者要行事曆權限。

**Token 儲存**：新 model `GoogleCalendarConnection`（1:1 對應行事曆空間），存 `refreshToken`/`accessToken`/`accessTokenExpiresAt`/`syncToken`。`refreshToken` 明碼存在資料庫欄位（沒有欄位層級加密）——這是延續這個 schema 一直以來的作法（`JWT_SECRET`、`RESEND_API_KEY` 等都是明碼環境變數），Postgres 本身的存取權限就是信任邊界，不是這次才決定的新取捨。

**`GoogleCalendarService`**：直接用 `fetch` 打 Google Calendar API v3 REST 端點（不加 `googleapis` 這個重量級 SDK 依賴，延續 LINE 整合那次「輕依賴」的作法），封裝：
- token 刷新（access token 快過期前 1 分鐘自動用 refresh token 換新的，順便存回資料庫）
- `listChanges(connection, syncToken)`：增量拉取異動，`syncToken` 是 Google 給的游標，過期（API 回 410）會自動改成全量重抓一次
- `insertEvent`/`updateEvent`/`deleteEvent`：推送本機異動

**雙向同步的兩個觸發點**（`CalendarSyncService.syncSpace`）：
1. 使用者開啟行事曆頁面時，前端呼又 `POST .../calendar/sync`
2. 背景：`@nestjs/schedule` 的 `@Cron(EVERY_5_MINUTES)`，掃過所有有連結 Google 的行事曆空間逐一同步——這只在 Render 服務醒著的時候才會跑（免費方案閒置會休眠），是「使用者開頁面時同步」的補充機制，不是唯一保證

每次同步做兩件事：拉 Google 異動套用回本機（`applyRemoteEvent`：狀態是 `cancelled` 就刪本機對應那筆、否則 upsert）；把本機還沒有 `googleEventId` 的事件（背景推送失敗過、或離線時新增的）重新嘗試推送一次。

## 五、LINE 行事曆整合

格式：`新增行事曆 日期 時間 項目 [@地點]`

- 日期：`M/D` 或 `YYYY/M/D`
- 時間：`H:MM`，或打「全天」代表整天活動
- 項目：活動標題
- `@地點`（選填）：結尾的 `@` 開頭字串當作地點，不寫就沒有地點

例：`新增行事曆 7/31 14:00 開會 @台北辦公室`、`新增行事曆 8/1 全天 生日`。

因為行事曆空間是 1:1 對應使用者（不像專案代辦事項要處理「使用者屬於好幾個專案」的多空間歧義），LINE 這邊不需要額外的「目前作用中空間」狀態，直接用 `calendarOwnerUserId` 查得到。寫入直接呼叫既有的 `CalendarEventsService.create()`（沒有繞過 HTTP service 層直接戳 Prisma，因為這個 service 已經處理好「背景推送到 Google」那段邏輯，直接重用比重寫一份 LINE 專用邏輯更省事、也不會兩邊邏輯之後長歪）。

## 六、使用者需要自己做的設定

**Google Cloud Console**：既有的 OAuth 用戶端（Desktop app 類型）要在「OAuth 同意畫面」的範圍設定加上 Google Calendar API 的 scope（`https://www.googleapis.com/auth/calendar`），並且要先在 Google Cloud 專案裡啟用 Calendar API。因為這是「敏感範圍」（sensitive scope），應用程式沒有通過 Google 驗證的話，第一次連結時瀏覽器會跳出「未驗證應用程式」的警告畫面——這是預期行為，使用自己的 Google 帳號時，選「進階 → 前往（不安全）」或者先把自己的帳號加進 OAuth 同意畫面的「測試使用者」名單即可繼續，不是程式錯誤。

## 七、發布流程（沿用）

1. commit + push 程式碼
2. 版本號同步改 `apps/windows_app/pubspec.yaml` 與 `apps/windows_app/installer/life_os.iss`
3. `rm -rf apps/windows_app/build/windows`（一定要做）
4. `flutter build windows --release`
5. 確認版本號：`(Get-Item apps\windows_app\build\windows\x64\runner\Release\life_os_app.exe).VersionInfo.FileVersion` 必須等於 pubspec 版本
6. `"C:\Users\chen6\AppData\Local\Programs\Inno Setup 6\ISCC.exe" installer\life_os.iss`
7. `gh release create vX.Y.Z installer/Output/life_os_setup.exe --title vX.Y.Z --notes "..."`

**資料庫 migration**：本機沒有 Docker，用 `npx prisma migrate diff --from-config-datasource prisma.config.ts --to-schema prisma/schema.prisma --script`（帶正式環境 `DATABASE_URL`）產生 migration SQL，寫進 `prisma/migrations/<timestamp>_xxx/migration.sql` 後 `npx prisma migrate deploy` 套用到正式環境。正式環境 `DATABASE_URL`（Supabase Session Pooler 連線字串）沒有存在任何本機檔案裡，每次需要都要請使用者重新提供。
