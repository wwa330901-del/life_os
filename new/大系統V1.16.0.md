# 第 16 步：首頁儀表板、側邊欄切換空間、記帳母子分類、工期表實際開始日期

## 零、給未來的我（Claude Code）

如果使用者說「我要寫大系統」，就是指這個系列文件（`new/大系統V1.1.0.md` ~ 目前最新版）跟 `C:\Users\chen6\Desktop\claude\life_os` 這個 monorepo。做法：

1. 讀這個系列裡最新版本的文件，掌握目前狀態
2. 直接在 `life_os` 目錄下繼續開發，延續「元序」這個產品
3. 每次程式有更動都要主動 commit + push 到 GitHub，不用使用者特別要求；使用者可見的改動還要照「發布流程」補做版本號/安裝檔/Release
4. 每次更新前後檢查 `life_os/problem feedback/` 資料夾裡有沒有使用者丟的截圖/回報
5. 需要視覺設計素材時，請使用者把圖片丟進 `life_os/Visual Design/`（這兩個資料夾都不進 git）
6. **Windows 發版前一定要先清掉 `apps/windows_app/build/windows` 再編譯**——這條寫過很多次了。

**這一版最重要的新東西：**
1. **工期表補上「實際開始日期」**——上一版只做了「實際工期(天)」這個數字，沒有日期就沒辦法定位在時間軸上，甘特圖也就沒東西畫。這次補上日期，甘特圖會在有紀錄的項目下方畫一條對照條，跟計畫進度直接比對。
2. **側邊欄可以直接切換空間**：點空間名稱列跳出選單，列出其他空間 + 回首頁選項，不用先回列表頁再選一次。
3. **記帳分類支援母/子分類**（兩層）：有子分類的母分類不能再直接記帳；總覽/報表/預算一律以母分類彙總；LINE 記帳同步更新。
4. **首頁儀表板**：空間卡片固定在最上方，下面新增可自訂的小工具區——個人財務狀況、本日支出及收入、專案總表（今日計畫 vs 實際）、本日代辦事項，使用者可以自己選要顯示哪些、怎麼排序，設定存後端跟著帳號走。

同時這一版也處理了行事曆的兩個實際 bug（全天活動同步到 Google 會跨時區位移一天、新增行程沒有結束時間欄位），以及 Google OAuth 驗證審核的前置作業（GitHub Pages 首頁/隱私權政策/App 標誌）進行中。

## 一、這次改動的起因

延續 V1.15.0（LINE 改回固定選單）之後，使用者一次丟出一輪需求：

1. 行事曆兩個 bug：「假設我在8/1新增全天行程...同步到google的時候會變成7/31全天」、「行事曆的活動如果不是全天應該要可以選擇開始時間跟結束時間，日期也一樣」
2. Google 行事曆連結在軟體內失敗（`Internal server error`）——追出根因是連結成功後緊接著自動觸發的第一次同步失敗，卻讓整個連結動作被誤判失敗
3. 準備 Google OAuth 驗證審核所需的素材（App 標誌），過程中使用者自己在 Google Cloud Console 操作時卡了幾個關卡（已授權網域格式、資料存取權範圍要手動加、品牌驗證失敗原因），這部分是使用者自己在 Google 那邊操作，我只負責準備素材跟排查錯誤訊息
4. 四項新功能需求（見上方摘要），對每一項的關鍵設計都先跟使用者確認過：
   - 首頁版面設定存後端（跟著帳號走）而不是只存本機
   - 記帳母分類有子分類時，必須選子分類記帳，不能直接選母分類
   - 首頁「今日進度」的判斷方式：今日應執行項目 vs 實際有紀錄的項目

## 二、行事曆兩個 bug 修正

**全天活動跨時區位移**：根因是前端把全天活動的日期用 `.toUtc()` 序列化——使用者在 UTC+8 環境選 8/1，本地時間解讀成「8/1 00:00 本地」，`.toUtc()` 轉換後變成「7/31 16:00 UTC」，這個 UTC 瞬間送到後端存下來，之後同步到 Google 用 `.toISOString().slice(0,10)` 取日期部分，拿到的自然是「7/31」。

修法：全天活動的日期不能當作「瞬間」處理，要當作單純的「日曆日期」——改成用選定的年月日直接建構一個「UTC 午夜」的時間送出（`DateTime.utc(y,m,d)`，不經過 `.toUtc()` 轉換），這樣年月日在整條路徑上都不會因為時區換算而偏移。有時段的活動不受影響（本來就用完整帶時區資訊的 `dateTime` 欄位，Google 那邊解讀正確）。

**新增行程沒有結束時間**：編輯視窗原本只有「日期」+「時間」（都只對應開始），沒有結束日期/時間欄位，`endAt` 從來沒有真正被送出去過。補上「結束日期」「結束時間」兩個欄位（非全天活動才顯示），預設結束時間 = 開始時間 + 1 小時，結束日期不能早於開始日期。

## 三、Google 行事曆連結的錯誤處理

**問題**：`CalendarConnectionController.connect()` 原本是「存 token → 立刻觸發一次同步」兩個步驟連續 await 沒有分開錯誤處理。Token 已經存成功了，但如果緊接著的第一次同步失敗（例如 Google Cloud 專案的 Calendar API 還沒啟用——這是使用者第一次測試時真的踩到的狀況，錯誤訊息是 `Google Calendar API has not been used in project ... or it is disabled`），整個 request 就丟出未捕捉例外，變成一片空白的「Internal Server Error」，讓使用者以為連結整個失敗，但其實 token 已經存進資料庫了。

**修法**：把「觸發首次同步」包一層 try/catch，失敗只記 log、不影響「連結成功」的回應（背景的 5 分鐘排程本來就會重試）。同時「立即同步」按鈕的端點也補上錯誤處理，失敗時回傳 Google API 實際的錯誤訊息（而不是空白 500），方便之後排查——這個改動直接讓使用者這次能看到「Calendar API 未啟用」這個真正的根因，而不是連續好幾輪靠猜。

## 四、工期表：實際開始日期 + 甘特圖對照條

**新欄位**：`WorkItem.actualStartDate DateTime? @db.Date`，跟既有的 `actualDurationDays` 搭配、各自獨立（可以只填一個）。工期表新增「實際開始日」欄位（日期選擇器，點兩下清除，樣式跟既有的「起始日」欄位一致）。

**甘特圖視覺化**：`GanttPainter._paintActualBar` 在有同時填 `actualStartDate` + `actualDurationDays` 的項目，於該列底部畫一條細的對照條（`GanttColors.actualBar`，跟 App 品牌一致的金色，跟計畫用的分類色階區分開來），純粹顯示比對用，不做進度填色、不加文字標籤。

同樣延續「刻意排除在匯出之外」的原則——匯出（Gantt 圖片/PDF）只呈現計畫排程，不含這兩個實際欄位。

## 五、側邊欄快速切換空間

`AppSidebar` 的空間名稱列，原本點了直接清空選取狀態回列表頁；現在改成彈出選單（`showMenu`，錨定在該列位置），列出使用者其他所有空間（含圖示區分個人/行事曆/公司），加一個「回首頁」選項在最後。選了其他空間直接 `selectedSpaceProvider.notifier.select(target)` 切過去，不用先回列表頁選一次。

## 六、記帳母/子分類

**資料模型**：`FinanceCategory` 新增 `parentId String?`（自關聯，`onDelete: Cascade`），唯一鍵改成 `[spaceId, name, kind, parentId]`（同一個母分類底下子分類名稱不能重複，但不同母分類底下可以同名）。**嚴格兩層**，在應用層強制（不是 DB constraint）：一個分類只能被設成別人的母分類，前提是它自己沒有母分類；一個分類如果自己底下已經有子分類，就不能再變成別人的子分類。

**交易規則**：有子分類的母分類不能再直接記帳（`FinanceTransactionsService.validate` 會擋，訊息「這個分類底下有子分類，記帳時要選子分類，不能直接選母分類」）；沒有子分類的母分類維持原本可以直接用。

**報表歸戶**：`monthlySummary`（總覽用的月度分類統計）改成一律以母分類彙總——一筆記在子分類的交易，在總覽/圖表裡算進它母分類的總額，子分類本身的名字不會出現在總覽/報表/預算，只有在交易明細列表才看得到（顯示成「早餐（飲食）」這種格式，母子都顯示）。預算改成只能設在母分類上（`FinanceBudgetsTab` 只列 `categories.topLevel`），`monthlyExpenseByCategory` 同時用子分類自己的 id 跟它母分類的 id 兩種 key 累加金額，確保無論預算設在哪一層都查得到正確花費。

**前端分類管理畫面**：`FinanceCategoriesTab` 改成階層顯示——母分類卡片 + 縮排的子分類卡片，每個母分類下面有「新增子分類」按鈕；編輯對話框可以改分類的母分類歸屬（如果自己底下已經有子分類就不能改，UI 會直接隱藏這個選項並顯示原因）。

**LINE 更新**：
- 「記帳」按鈕的格式說明改成只列「子分類（或沒有子分類的母分類）」名稱，母分類本身如果有子分類就不會出現在清單裡——因為使用者永遠只會打子分類，系統自動歸類到母分類。
- 範例從原本三種分隔符號並列（空格/符號/黏在一起）簡化成只給一個黏在一起的例子（「支出300午餐現金」），因為分隔符號本來就不拘，不需要每種都示範一次。
- 一行指令解析（`parseFinanceCommand`）比對分類名稱時，改成只在「葉節點」分類（`leafCategories` 輔助函式：排除掉所有被別人當母分類引用的那些）裡找，不會誤配到有子分類的母分類名稱。

## 七、首頁儀表板

**核心決定**：空間卡片固定在最上方、不受版面自訂影響；下面新增可自訂顯示/排序的小工具區。版面設定（`User.homeLayoutConfig Json?`）存在後端跟著帳號走（不是本機/瀏覽器層級的偏好）——這個決定是因為這個 App 的其他所有資料都是伺服器為準，本機儲存偏好會是唯一的例外，換電腦/重灌就會不一致。

**四個預設小工具**（`DEFAULT_WIDGET_TYPES`，一個新使用者、或還沒動過版面設定的舊使用者，預設全部顯示）：
- `personalFinance` 個人財務狀況：個人空間每個帳戶的即時餘額
- `todayFinance` 本日支出及收入：個人空間今天的收入/支出總額
- `projectSummary` 專案總表：使用者所屬每個專案，「今日計畫應執行的工項」vs「今日實際有紀錄的工項」比對——用的正是這次剛做的「實際開始日期」欄位。計畫但沒有對應實際紀錄的項目會標紅字提示「可能落後」。完全沒有計畫項目、也沒有實際紀錄的專案當天不會出現在清單（避免洗版）。
- `todayTodos` 本日代辦事項：跨所有專案（不分是哪個），今日已完成 + 今日到期未完成，各自列出並標註所屬專案

**後端**：新的 `HomeModule`（`GET /home/dashboard` 一次算完四塊資料、`GET/PUT /home/layout` 讀寫版面設定）。`getLayout` 對「使用者存的設定裡缺少的小工具類型」自動補上預設可見——用意是之後如果又新增第五個小工具，已經自訂過版面的舊使用者不會因為存量設定沒有這個 key 就永遠看不到它，一定會先出現一次讓使用者自己決定要不要關掉。`projectSummary` 的「今日計畫應執行」直接重用 `ScheduleService.buildEditorState`（跟工期表分頁用的是同一套排程引擎，兩邊看到的日期保證一致）。

**前端**：`SpacePickerScreen`（首頁＝空間選擇頁，兩者是同一個畫面）從原本置中的卡片 `Wrap` 改成可捲動的 `Column`——卡片區塊在最上面維持原樣，下面加「首頁總覽」標題 + 「自訂版面」按鈕 + 依版面設定渲染的小工具卡片列表。自訂版面用 `ReorderableListView` + `CheckboxListTile`（可勾選顯示/隱藏、拖曳排序），存檔呼叫 `PUT /home/layout`。

## 八、發布流程（沿用）

1. commit + push 程式碼
2. 版本號同步改 `apps/windows_app/pubspec.yaml` 與 `apps/windows_app/installer/life_os.iss`
3. `rm -rf apps/windows_app/build/windows`（一定要做）
4. `flutter build windows --release`
5. 確認版本號：`(Get-Item apps\windows_app\build\windows\x64\runner\Release\life_os_app.exe).VersionInfo.FileVersion` 必須等於 pubspec 版本
6. `"C:\Users\chen6\AppData\Local\Programs\Inno Setup 6\ISCC.exe" installer\life_os.iss`
7. `gh release create vX.Y.Z installer/Output/life_os_setup.exe --title vX.Y.Z --notes "..."`

**資料庫 migration**：本機沒有 Docker，用 `npx prisma migrate diff --from-config-datasource prisma.config.ts --to-schema prisma/schema.prisma --script`（帶正式環境 `DATABASE_URL`）產生 SQL，`npx prisma migrate deploy` 套用到正式環境。正式環境連線字串沒有存在任何本機檔案裡，每次需要都要請使用者重新提供。
