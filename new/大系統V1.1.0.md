# 1. 產品定位

本產品不是單一記帳軟體、筆記軟體、ERP、PMIS 或 Notion 替代品，而是一套：

> **供個人、公司、組織與專案團隊共同使用的模組化數位作業平台。**

整體概念為：

- Notion 型自由文件與資料庫
- PMIS 專案與工程管理
- ERP 公司營運管理
- 個人記帳與資產管理
- 行事曆與工作安排
- 學習、旅遊、美食、筆記等個人模組
- LINE 快速輸入與查詢
- AI 智慧助理
- 可持續擴充的新模組

系統必須以「共用平台核心」為底座，讓所有模組共用帳號、權限、資料關聯、搜尋、通知、行事曆、檔案、AI 與操作紀錄，而不是把多個互不相通的小系統拼接在一起。

# 3. 帳號與空間

## 3.1 單一帳號

每位使用者只需要一組帳號與密碼登入。

登入後，依照權限切換不同空間，例如：

```text
陳風竹
├── 個人空間
├── 境為室內裝修
├── 境泰建設
├── 建築師事務所
├── 校友會
└── 松山分行專案
```

## 3.2 空間類型

### 個人空間

只屬於個人本人，包含：

- 個人記帳
- 投資
- 私人行程
- 學習
- 筆記
- 旅遊
- 美食
- 日記
- 人生目標

### 公司空間

供公司成員共同使用，包含：

- 公司營運
- 專案
- 人資
- 財務
- 採購
- 合約
- 客戶
- 廠商
- 簽核
- 公司行事曆
- 文件

### 專案空間

供特定專案成員使用，包含：

- 業主
- 建築師
- 設計師
- 工務
- 廠商
- 顧問
- 專案文件
- 任務
- 進度
- 請款
- 施工日誌

## 3.3 資料隔離

不同空間的資料必須隔離。

使用者只能查看：

- 自己被授權的公司
- 自己被授權的專案
- 自己被授權的模組
- 自己被授權的資料與欄位

任何個人資料、公司財務、薪資、利潤、敏感文件與 AI 查詢結果，都必須受權限限制。

# 4. 個人帳、公司帳與專案帳

## 4.1 基本原則

個人帳、公司帳與專案帳必須分開。

資料可以互相關聯，但帳戶、帳本與正式交易紀錄不能混在一起。

## 4.2 公司代墊案例

### 代墊發生時

使用者先以個人信用卡支付公司材料費 3,000 元。

#### 個人端

```text
支出：3,000元
類別：公司代墊
付款帳戶：個人信用卡
請領狀態：尚未請領
關聯公司：境為
關聯專案：松山案
```

#### 公司端

```text
代墊紀錄：3,000元
代墊人：陳風竹
狀態：待請領
關聯專案：松山案
```

此時公司尚未付款，因此公司銀行帳戶尚不產生正式支出。

### 公司完成請領後

#### 個人端

```text
收入：3,000元
類別：公司代墊返還
收款帳戶：個人銀行
關聯原始支出：3,000元
```

#### 公司端

```text
支出：3,000元
類別：專案材料費
付款帳戶：公司銀行
收款人：陳風竹
關聯代墊紀錄：原代墊單
```

### 完整關聯

```text
個人原始支出
    ↕
公司代墊申請
    ↕
公司付款支出
    ↕
個人返還收入
```

四筆紀錄可互相追蹤，但各自存在不同帳本與帳戶中。

# 5. LINE 的定位

LINE 不是主系統，也不是主要資料庫。

LINE 是：

> **快速輸入資料、快速查詢資料、接收通知與執行簡易操作的入口。**

正式資料仍儲存在平台後端與資料庫。

## 5.1 LINE 輸入功能

LINE 可用於：

- 快速記帳
- 公司代墊
- 建立任務
- 建立行程
- 紀錄施工進度
- 建立施工問題
- 上傳工地照片
- 上傳收據
- 上傳文件
- 語音轉文字
- 填寫簡易表單
- 建立採購草稿
- 建立請款草稿

例如：

```text
今天松山案買乳膠漆3,000元，我先刷卡。
```

系統應辨識並建立：

- 個人代墊支出
- 公司待請領紀錄
- 松山案成本草稿
- 收據補件提醒

## 5.2 LINE 查詢功能

LINE 可作為資料查詢出口。

例如：

```text
台北市哪裡有好吃的牛肉麵？
```

系統應優先搜尋個人資料庫：

- 曾記錄的餐廳
- 曾去過的餐廳
- 收藏但未造訪的餐廳
- 個人評分
- 同行者
- 價格
- 地點
- 最近造訪日期
- 個人備註

未來可採以下查詢順序：

1. 先搜尋使用者自己的資料庫。
2. 找不到時，詢問是否搜尋外部網路。
3. 將外部搜尋結果保存到收藏資料庫。

## 5.3 LINE 與系統帳號

LINE 身分與正式系統帳號必須分開。

正式身分仍以系統帳號為主，LINE 只是綁定入口。

即使使用者更換 LINE、手機遺失、取消綁定或離職，正式資料仍屬於系統帳號。

# 6. AI 的定位

AI 不是單一聊天頁面，而是整套平台的智慧層。

AI 可以：

- 理解 LINE 訊息
- 自動分類資料
- 建立任務
- 建立行程
- 建立記帳草稿
- 整理會議紀錄
- 整理施工日誌
- 查詢專案資料
- 分析專案進度
- 分析財務
- 分析成本異常
- 產生週報
- 找出延誤風險
- 回答公司制度
- 搜尋歷史案例
- 提醒未完成承諾

## 6.1 AI 權限原則

AI 不能超越使用者本身的權限。

例如，工務若沒有財務權限，即使詢問 AI 專案花費，AI 也不能回答。

## 6.2 AI 操作紀錄

每次 AI 操作都必須留下：

- 誰提出要求
- AI 讀取了哪些資料
- AI 建議了什麼
- AI 修改了哪些資料
- 是否經人工確認
- 修改前內容
- 修改後內容
- 操作時間

## 6.3 AI 執行等級

AI 權限至少分為：

- 只讀
- 建議
- 待確認執行
- 自動執行

以下高風險行為不得無確認執行：

- 刪除資料
- 發送訊息
- 金錢交易
- 投資交易
- 重要行程異動
- 分享隱私資料
- 帳號與權限變更

# 8. 擴充性原則

每個系統與模組都必須保留未來擴充能力。

任何功能不得寫死成只適用目前情境。

每個模組至少要保留：

- 自訂欄位
- 自訂狀態
- 自訂分類
- 模組關聯
- API 接口
- 權限接口
- 自動化接口
- AI 工具接口
- 未來多平台接口

但不得因為未來可能使用，就一次開發過度複雜的功能。

正式原則為：

> **結構可以擴充，功能分階段完成。**

# 14. 資料庫與後端優先原則

不能先完成整套介面，最後才補資料庫。

正確順序：

```text
確認平台骨架
↓
同步設計介面與資料模型
↓
建立正式資料庫與後端
↓
Windows 接上真實資料
↓
LINE 接上同一套後端
↓
開始實際使用
↓
根據問題持續修正
```

從第一個可使用版本開始，資料就必須存在正式後端。

本機可以有：

- 快取
- 離線資料
- 等待同步資料

但雲端資料庫才是主要資料來源。

開發方式必須採：

> **一邊使用、一邊開發、一邊測試、一邊修正。**

# 15. 正式確認的 14 項產品原則

1. 所有功能放在同一套平台。
2. 最終支援 Windows、macOS、iOS、Android 與 Web。
3. 每個人使用自己的帳號密碼登入。
4. 一個帳號可以加入多間公司、組織與專案。
5. 個人、公司與專案帳戶分開，但資料可以互相關聯。
6. 不同角色看到不同資料與功能。
7. LINE 是快速輸入與快速查詢出口。
8. AI 可以跨模組協助，但不得超越使用者權限。
9. 系統可以持續新增模組。
10. 先建立共用平台核心，不直接拼湊大量獨立功能。
11. 每個模組必須保留擴充能力，介面與功能同步設計。
12. 第一階段採 Windows + LINE，並從一開始接上正式資料庫與後端。
13. 介面設計包含功能排版、視覺風格、背景、圖樣、插圖與圖片；功能頁必須以清晰易用為優先。
14. 平台必須具備系統管理中心與一般使用者設定區。

## 16.2 AI 規劃者角色

AI 規劃者負責：

- 深化需求
- 補足遺漏功能
- 檢查邏輯衝突
- 規劃系統架構

- 規劃介面
- 拆解 Claude Code 工作
- 撰寫可直接貼給 Claude Code 的指令
- 說明 Claude Code 應做什麼
- 安排測試
- 設定驗收標準
- 分析錯誤
- 產生修正指令

## 16.3 Claude Code 的角色

Claude Code 是受規範的開發工程師，而不是產品決策者。

Claude Code 不得：

- 自行改變產品方向
- 自行新增未確認需求
- 自行跳過步驟
- 為了修錯而刪除既有功能
- 將功能寫死
- 將密鑰寫進程式碼
- 未測試就宣稱完成

- 通過
- 部分通過
- 失敗

## 17.8 問題修正

使用者提供錯誤畫面或錯誤訊息後，AI 規劃者先分析，再產生修正指令。

# 18. 強制逐步確認規則

整個開發流程採「逐步確認制」。

固定規則：

- 一次只處理一個步驟。
- 不會因前一步完成就自行開始下一步。
- 每一步完成後必須停止。
- 只有使用者明確說「下一步」後，才能進入下一步。
- 使用者提出新想法時，先納入總體規劃，不直接破壞目前開發順序。
- 每個重要修改都必須可以測試、追蹤與回復。
- 不一次要求 Claude Code 開發整套系統。
- 先規劃，再下指令。
- 先測試，再往後走。
- 未取得使用者確認，不得自行推進。
