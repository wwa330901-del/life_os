## 一、這次改動的起因

延續 V1.12.0 之後，使用者一次丟了 7 項需求（LINE 選單改 Rich Menu、LINE 財務總覽、專案代辦事項、代辦事項 LINE 整合、行事曆空間+Google同步、實際工期欄位、AI 整合）。逐項討論範圍後，使用者明確要求分輪做：

> 「分輪做：這輪先完整做完代辦事項（包含LINE整合），下輪再做行事曆空間+Google同步，最後做AI」

所以行事曆空間、Google 行事曆雙向同步、AI/ChatGPT 整合都是**刻意延後、還沒開始**的項目，不要誤以為漏掉了。

範圍確認時使用者對每個題目都選了最完整的選項：
- 代辦事項欄位：進階（標題、完成與否、截止日、優先順序、指派給誰、備註）
- （行事曆/AI 相關的範圍確認留給下一輪，這裡先不重複）

另外使用者中途問了一個很關鍵的問題：「如果我朋友加了我這個官方 LINE 帳號，也下載了軟體，會自動連線嗎？」——答案是不會，`LineAccountLink` 一定要透過綁定碼交換才會建立，單純加好友/裝軟體兩件事互不影響，這個機制在 V1.12.0 已經做好，這裡只是再次確認沒有意外風險。

## 二、實際工期欄位（v0.17.0）

`WorkItem` 新增 `actualDurationDays Int?`，跟既有的「工期(天)」（預計）並列成獨立欄位。前端 `task_table.dart` 在原本工期欄旁邊多一欄「實際工期(天)」，同樣是可編輯的文字欄位，透過 `ProjectEditorNotifier.changeActualDuration(id, days)` → `TaskTable` 的 `onActualDurationChanged` 回呼寫回。這欄位刻意**不**放進 Excel/文件匯出邏輯，維持匯出結果只反映「計畫」而非「執行落差」。

## 三、LINE 財務總覽指令（v0.17.0）

在 LINE 對話裡傳「總覽」（或「財務總覽」「總覽財務」），機器人回傳：目前所有帳戶餘額、本日總支出/收入、本月總支出/收入。實作上重用既有的 `FinanceAccountsService.list()` 和 `FinanceTransactionsService.monthlySummary()`，另外直接查一次「今天」區間的交易做本日統計，組成一段文字用 Reply API 回覆。

## 四、專案代辦事項（ProjectTodo）

**新 Prisma model**：

```prisma
enum TodoPriority { LOW MEDIUM HIGH }

model ProjectTodo {
  id        String  @id @default(uuid())
  projectId String
  project   Project @relation(fields: [projectId], references: [id], onDelete: Cascade)

  title       String
  done        Boolean   @default(false)
  completedAt DateTime?
  dueDate     DateTime? @db.Date
  priority    TodoPriority @default(MEDIUM)
  notes       String?

  assigneeUserId String?
  assignee       User?   @relation(fields: [assigneeUserId], references: [id], onDelete: SetNull)

  sortOrder Int      @default(0)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([projectId])
}
```

跟工項（`WorkItem`）刻意分開，不共用資料表——代辦事項沒有工期、不進甘特圖排程，是純粹的任務清單，這是需求討論時就確定的（工進表是「排程」，代辦事項是「雜項任務」，語意不同）。

**後端**：`ProjectTodosService`（`list`/`create`/`update`/`remove`），存取控制沿用 `ProjectsService.getProjectOrThrow` + `assertAccess`；`assigneeUserId` 若有填，會用 `ProjectMember` 的 `userId_projectId` 複合鍵驗證「指派對象必須是這個專案的成員」，否則丟 400。`update()` 在 `done` true/false 切換時自動設定/清空 `completedAt`。路由掛在 `projects/:projectId/todos`。

**前端**：`ProjectDetailScreen` 新增第 5 個分頁「代辦事項」，`ProjectTodosTab` 用 FAB 新增，列表用優先順序色點 + 完成打勾 + 逾期紅字提示，點擊項目可編輯（標題/截止日/優先順序/指派/備註），指派下拉選單資料來源是 `projectMembersProvider`。

## 五、代辦事項的 LINE 整合

**核心問題**：記帳的 LINE 綁定是「使用者 ↔ LINE 帳號」1:1，記帳資料本身也是掛在使用者的個人空間下，天生沒有「哪一筆資料屬於哪個空間」的歧義。但代辦事項是掛在「專案」底下，一個使用者可能同時是好幾個專案的成員，LINE 傳「新增買材料」的時候，機器人不知道要記到哪個專案。

**解法**：`LineAccountLink` 新增 `activeProjectId`（nullable，指向 `Project`）記住「目前這個 LINE 帳號操作代辦事項時，作用中的專案是哪個」。

- 傳「代辦」「代辦事項」「待辦」「待辦事項」任一個關鍵字進入代辦模式：`enterTodoFlow` 檢查目前使用者是哪些專案的成員（`prisma.projectMember.findMany({where:{userId}, include:{project:true}})`），如果剛好只有一個專案就自動設成 `activeProjectId`；如果有多個，用 Quick Reply 列出專案名稱給使用者選（postback `data: 'proj:<id>'`），選完才設定。
- 「新增OOO」→ 去掉「新增」前綴後，直接對 `activeProjectId` 建立一筆 `ProjectTodo`（標題 = 去除前綴後的文字）。
- 「完成OOO」→ 先精確比對標題，找不到再做子字串比對；找不到或有多筆符合都會回覆說明，不會亂猜。
- **總覽**：`sendTodoOverview(projectId, replyToken)` 統計「今日已完成」（`completedAt` 是今天）、「今日到期未完成」（`dueDate` 是今天且未完成）、「未來 7 天到期」（`dueDate` 在接下來 7 天內且未完成），組成文字回覆。

這幾個分支全部在 `LineService.handleTextForLinkedUser` 裡依序判斷（總覽關鍵字 → 代辦進入關鍵字 → 「切換專案」→「新增」開頭 → 「完成」開頭 → 記帳相關 pending/一行指令 → 都不是才進記帳引導式選單），跟記帳共用同一個 webhook 入口但邏輯互不干擾。

跟 `ProjectTodosService`（HTTP 層用的 service）不同，LINE 這邊寫入代辦事項一樣是直接呼叫 Prisma（沿用 V1.12.0 記帳整合就定下的模式：LINE 走 webhook，不繞經 HTTP controller 層），`LineModule` 因此不需要 import `ProjectsModule`。

## 六、LINE Rich Menu 三按鈕化

原本（V1.12.0）是二按鈕（記帳/財務總覽），這次改成三等分的三按鈕：記帳／財務總覽／代辦事項。做法跟上次一樣，用 `sharp` 套件把手寫的 SVG 光柵化成 2500×843px 的 PNG（深色底、三欄用細直線分隔，每欄一個 emoji icon + 文字標籤），再用一支一次性 Node 腳本：

1. `GET /v2/bot/richmenu/list` 列出現有選單，逐一 `DELETE` 清掉舊的（避免累積孤兒選單）
2. `POST /v2/bot/richmenu` 建立新選單定義（3 個等寬 `areas`，各自的 `action` 是 `{type: 'message', text: '記帳'|'總覽'|'代辦事項'}`）
3. `POST https://api-data.line.me/v2/bot/richmenu/{id}/content` 上傳 PNG
4. `POST /v2/bot/user/all/richmenu/{id}` 設成所有使用者的預設選單

Channel access token 全程只透過環境變數傳入腳本，用完即刪腳本和暫存圖檔，不寫進程式碼或 git。

（備註：`sharp` 光柵化 SVG 時 emoji 會變成單色黑白圖示，不是全彩，這是 SVG 渲染引擎沒有彩色 emoji 字型的關係——圖示仍然清楚可辨識，先接受這個限制，不算 bug。）
