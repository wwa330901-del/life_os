# 第 15 步：LINE 改回固定選單＋彈性一行指令、行事曆連結錯誤處理修正

## 零、給未來的我（Claude Code）

如果使用者說「我要寫大系統」，就是指這個系列文件（`new/大系統V1.1.0.md` ~ 目前最新版）跟 `C:\Users\chen6\Desktop\claude\life_os` 這個 monorepo。做法：

1. 讀這個系列裡最新版本的文件，掌握目前狀態
2. 直接在 `life_os` 目錄下繼續開發，延續「元序」這個產品
3. 每次程式有更動都要主動 commit + push 到 GitHub，不用使用者特別要求；使用者可見的改動還要照「發布流程」補做版本號/安裝檔/Release（**這次是純後端改動，沒有動到 Windows App，所以沒有新版本號/安裝檔**）
4. 每次更新前後檢查 `life_os/problem feedback/` 資料夾裡有沒有使用者丟的截圖/回報
5. 需要視覺設計素材時，請使用者把圖片丟進 `life_os/Visual Design/`（這兩個資料夾都不進 git）
6. **Windows 發版前一定要先清掉 `apps/windows_app/build/windows` 再編譯**——這條寫過很多次了。

**這一版最重要的新東西：**
1. **LINE 底部選單切換機制（V1.14.0 才剛做的）整個拿掉了**——根本原因是 Render 的 Linux 環境沒有中文字型，伺服器端動態畫的選單圖片裡中文字全部變成亂碼/空白方塊。改回**固定的靜態選單**（記帳/財務總覽/代辦事項/代辦事項總覽 四宮格，在本機 Windows 畫好圖上傳，本機有中文字型不會有這個問題）。
2. **記帳指令變得更聰明**：分隔符號完全不拘，甚至可以整串黏在一起打（「支出300午餐現金」），靠掃描使用者自己的分類/帳戶名稱當子字串來定位，不是憑位置切token——這個做法也順便解決了舊版一行指令「分類會變成備註」的老問題。
3. **代辦事項「完成」改用編號**，不用打標題（跟上一次顯示的清單對應），解決「新增跟完成打的字可能不一樣，容易比對不到」的問題。
4. **Google 行事曆連結的一個真實 bug 修好了**：連結成功但第一次同步失敗時，原本會把整個連結動作誤報成失敗（其實 token 已經存好了）。
5. **開始準備 Google OAuth 驗證審核**，讓「連結 Google 行事曆」未來能開放給任何人用，不用手動加測試名單——目前進度：GitHub Pages 首頁/隱私權政策/App 標誌都做好了，卡在 Google Cloud Console 那邊的網域驗證跟後續送審，是使用者自己在 Google 那邊操作，不是程式問題。

## 一、這次改動的起因

延續 V1.14.0（LINE 記帳改用底部選單依序切換）之後：

1. 使用者實際測試新流程，回報「line的功能出現亂碼」——追查後發現是 V1.14.0 新增的 `LineRichMenuService`（用 `sharp` 在**伺服器端**即時把分類/帳戶名稱畫成選單圖片）在 Render 的 Linux 環境沒有中文字型可用，中文字全部變成亂碼。
2. 使用者藉這個機會直接要求整個設計改向：「還是不要用選單的方式好了，只需要保留記帳、財務總覽、代辦事項...點選後會依序跳出輸入格式提醒及選單」，並且明確要求輸入格式的分隔符號要盡量不侷限（討論後確認：連完全不留分隔符號都要能解析）。
3. 使用者也主動問了一個好問題：「代辦事項完成時，我要如何簡單地說就能馬上判斷是哪一個項目」——這是我建議、使用者採納的「編號」方案：每次顯示代辦清單都重新編號，完成時打編號就好，不用打標題。
4. 使用者接著决定要讓「連結 Google 行事曆」開放給任何人使用（不只是手動加測試帳號），這需要通過 Google 的 OAuth 驗證審核，於是準備了首頁、隱私權政策、App 標誌，過程中發現 Google Cloud Console 對「已授權網域」的填法有限制（不能填 `github.io` 這種公用網域，要填完整的 `wwa330901-del.github.io`）。
5. 使用者實際錄製驗證用的示範影片時，發現「連結 Google 行事曆」在軟體內失敗，回報 `Internal server error`——追出是連結授權成功後緊接著自動觸發的第一次同步，如果失敗（例如 Calendar API 還沒在 Google Cloud 專案啟用），會讓整個連結動作被誤判失敗。

## 二、為什麼放棄「底部選單依序切換」

**根本原因**：`LineRichMenuService.createSelectionMenu` 用 `sharp` 把 SVG 光柵化成 PNG，這個光柵化動作是在後端（Render，Linux 容器）即時執行的。SVG 裡指定的中文字型（`Microsoft JhengHei`／`PingFang TC`）是 Windows／macOS 內建字型，Linux 容器裡完全沒有，`librsvg`（sharp 底層用來畫 SVG 的引擎）找不到可用的中文字型，畫出來的中文字就是亂碼或空白方塊。

**這跟主選單（記帳/財務總覽/代辦事項/代辦事項總覽）不一樣**：主選單的圖片是我在**本機 Windows**（有中文字型）畫好、直接上傳一張**靜態圖片**，過程中不會在 Render 上動態產生任何文字圖片，所以完全沒有這個問題。這也是這次修法的核心：**只要牽涉到把中文字動態畫成圖片、且是在 Render 上執行，就一定會踩到這個坑**——之後如果還有類似需求（例如又想做動態選單），要嘛把畫圖搬回本機做、要嘛在 Render 容器裡裝中文字型（Dockerfile 自訂，Render 目前用的是 buildpack 自動偵測，沒有簡單的裝字型方式），兩者都不是這次的範圍。

**移除的東西**：`line-rich-menu.service.ts` 整個檔案刪除、`LineAccountLink.pendingDraft`／`pendingRichMenuId` 兩個欄位刪除（改用更簡單的 `lastTodoListIds`）、`@nestjs/schedule` 沒有受影響（行事曆同步的 cron 還在用）、`sharp` 從 `apps/api` 的 `package.json` 移除（不再需要，只有生成一次性靜態選單圖片時才用得到，那個是本機一次性腳本，不是專案依賴）。

## 三、記帳指令：分隔符號不拘 + 子字串比對分類/帳戶

**格式**：`支出/收入 金額 分類 帳戶 備註`，順序固定，但每個欄位之間可以是空格、`-`、`+`、`*`、`/`、逗號、頓號等任意符號混用，甚至完全不留分隔符號。

**解析邏輯**（`LineService.parseFinanceCommand`）：
1. 開頭比對「支出」或「收入」（固定關鍵字，不需要分隔符號）
2. 緊接著抓數字（`^\d+(\.\d+)?`）當金額
3. **分類跟帳戶不是照位置切 token，是拿使用者自己在 App 裡設定的分類/帳戶名稱，去剩餘文字裡找子字串**（名稱長的先比對，避免短名稱誤判，例如同時有「餐」跟「早餐」兩個分類時「早餐」要先比對到），找到就從文字裡挖掉那一段
4. 分類、帳戶都比對完之後，剩下的文字（去掉頭尾殘留的分隔符號）就是備註

這個「掃已知詞彙庫」的作法同時解決了兩件事：一是完全不留分隔符號的輸入也能正確解析（因為不依賴分隔符號切位置），二是意外修好了更早之前「一行指令分類會變成備註」的老問題（因為現在分類是真的被辨識出來、不是整段被塞進備註）。

**點擊「記帳」按鈕**（`sendFinanceHelp`）：不會啟動任何多步驟流程，只是回一則文字，列出輸入格式範例，以及該使用者目前實際的支出分類、收入分類、帳戶名稱清單——讓使用者知道打什麼字會被正確辨識。

## 四、代辦事項：完成改用編號

**新欄位**：`LineAccountLink.lastTodoListIds String[]`——每次「代辦事項」或「代辦事項總覽」顯示清單時，把當時顯示的、**未完成**的代辦事項 id 依顯示順序整組存進這個欄位（已完成的項目只是列出來參考，不編號，因為沒有「完成」這個動作可以對它做）。

**完成指令**：「完成 2」直接用 `lastTodoListIds[1]` 查出對應的 `ProjectTodo`，不用打標題，也不會有「新增打的字」跟「完成打的字」對不起來、或子字串比對比到多筆的問題。編號在同一份清單裡不會因為完成掉某一項而重新洗牌——完成過的編號再打一次，會回覆「已經是完成狀態了」。

**兩個按鈕的差別**：
- 「代辦事項」（`sendTodoHelp`）：目前作用中專案（`activeProjectId`，沒設定的話跟以前一樣用 quick-reply 選一個）的未完成清單，附新增/完成的格式說明。
- 「代辦事項總覽」（`sendTodoOverviewAllProjects`，新增）：不分專案，一次列出使用者所有專案「今日已完成」「今日到期未完成」「未來7天到期」，未完成的兩組連續編號，完成的僅列出參考。今日已完成/未完成清單顯示時各自標註是哪個專案的。

「新增 XXX」還是要有 `activeProjectId`（一個代辦事項一定屬於某個專案，這點沒變），「完成 N」則完全不需要，因為是靠 `lastTodoListIds` 直接查 id，不管那筆屬於哪個專案。

## 五、行事曆指令的同款彈性解析

`parseCalendarCommand`（「新增行事曆 日期 時間 項目 [@地點]」）也一起改成正規表達式定錨解析，不再單純用空白切 token：日期（`M/D` 或 `YYYY/M/D`）跟時間（`H:MM` 或「全天」）本身就有 `/`、`:` 這種自帶分隔特性的字元，靠這個直接從黏在一起的文字裡把日期、時間切出來；地點用結尾的 `@地點` 抓，其餘當標題。跟記帳指令一樣，分隔符號有沒有留都能解析。

## 六、Google 行事曆連結的錯誤處理修正

**問題**：`CalendarConnectionController.connect()` 原本是「存 token → 立刻觸發一次同步」兩步驟連續 await，沒有分開處理錯誤。如果 token 已經存成功，但緊接著的第一次同步失敗（例如 Google Cloud 專案還沒啟用 Calendar API——這是跟「OAuth 同意畫面範圍設定」完全分開的另一個開關，很容易漏做），整個 request 就會丟出未捕捉的例外，Nest 預設回傳一片空白的「Internal Server Error」，讓使用者以為連結整個失敗，但其實 token 已經存進資料庫了。

**修法**：把「觸發首次同步」包一層 try/catch，失敗只記 log、不影響「連結成功」的回應——反正背景的 5 分鐘排程本來就會重試。另外 `GoogleCalendarService.connect()` 也把「跟 Google 交換 code」這步包了 try/catch，失敗時丟出有意義的訊息（「跟 Google 交換授權失敗，請重新連結一次」）而不是讓原始例外直接炸穿到最外層變成無意義的 500。

## 七、準備 Google OAuth 驗證審核（進行中，使用者自己操作那部分）

為了讓「連結 Google 行事曆」未來對任何人開放（不用手動加測試使用者），需要通過 Google 的 OAuth 驗證審核（行事曆屬於「敏感範圍」）。已經準備好的東西：

- 應用程式首頁：`https://wwa330901-del.github.io/life_os/`
- 隱私權政策：`https://wwa330901-del.github.io/life_os/privacy-policy.html`
  （放在獨立的 `gh-pages` 分支，跟主線程式碼、`docs/問題排除紀錄.md` 這類內部文件完全分開，不會不小心公開到不該公開的東西）
- 應用程式標誌：`Visual Design/元序應用程式標誌.png`（512x512，深色底金色「元」字，本機生成，符合 Google 最低 120x120px 正方形的要求）

完整申請步驟寫在使用者桌面的 `Google行事曆驗證申請流程.md`（不在 repo 裡，純粹是給使用者看的操作說明）。過程中的幾個坑：
- Google Cloud Console「已授權網域」欄位不能填 `github.io`（公用網域，Google 的 Public Suffix List 擋掉），要填完整子網域 `wwa330901-del.github.io`
- 這個欄位要填得進去，前提是先在 Google Search Console 用「URL 前置字元」類型（不是「網域」類型）驗證 `https://wwa330901-del.github.io/life_os/` 的所有權，用 HTML 標籤驗證法（meta 標籤已經加進首頁 `<head>` 了）
- 「應用程式服務條款」欄位是選填，使用者確認不需要，留空即可
- 這整套流程完全免費（Calendar API 額度很高且不需要開通帳單；審核本身免費，除非用到「受限範圍」才需要付費資安評估，行事曆屬於「敏感範圍」不是「受限範圍」）
- 送審通常需要示範影片，內容要包含完整的 Google 授權同意畫面（讓審核人員看到範圍敘述）

這一步的後續進度（網域驗證有沒有過、有沒有正式送審、審核結果）要問使用者，不是程式碼能自己確認的狀態。
