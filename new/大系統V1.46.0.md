# 大系統 V1.46.0（2026-08-05）

延續知識庫/代辦事項的「無上限查詢」通盤檢討，這輪處理分身抓出來的其餘 6 項裡的 4 項；另外 2 項（持股計算、借貸/代墊列表）遇到結構性問題，先記錄下來、不動。

## 修好的 4 項

1. **`FinanceAccountsService.computeBalanceDeltas`（帳戶餘額計算）**——全專案跑最頻繁的路徑（每次看記帳畫面、每次 LINE 記帳/財務總覽指令都會呼叫），過去是把空間有史以來全部交易整批撈出來在 Node 裡加總。改成兩個 Prisma `groupBy` 聚合查詢（先依 `accountId+type` 分組加總，再單獨處理 TRANSFER 的 `toAccountId` 那一側），直接在資料庫端加總——因為單純線性加總沒有順序性，改寫前後數學上完全等價，查詢成本從「跟交易數量成正比」變成「跟帳戶數×交易類型數成正比」。
2. **`home.service.ts` 的 `getTodosToday()`**——這是代辦事項那批 bug 的第三個漏網分身（`TodosService.listAll` 跟 `LineService.sendTodoOverviewAllProjects` 這次通盤檢討之前的那輪就修了，這個首頁小工具用的方法沒抓到）。查詢改成只抓「今天完成」或「今天到期且未完成」兩種真正會用到的資料，比 `TodosService.listAll` 用的過濾邏輯更精準（那邊要顯示所有未完成不分日期，這裡只要今天的）。
3. **`DocumentApprovalsService.mySubmissions`（我送出的簽核）**——改成游標分頁（30 筆一頁），App「簽核」畫面的「我送出的」分頁加上無限捲動，寫法跟知識庫/代辦事項已完成分頁同一套（`AsyncNotifierProvider` + `ScrollController`）。
4. **`StocksTransactionsService.list`（股票交易明細）**——同樣改成游標分頁（30 筆一頁），App 股票交易列表加無限捲動。

以上都跟知識庫/代辦事項一樣的處理方式，因為都是「單純的顯示列表，沒有其他地方依賴它回傳完整未篩選的資料」。

## 先記錄、不動的 2 項

**持股計算（`StocksHoldingsService.list`）**：均價成本法是**有順序性**的算法——每次賣出是照「當下」的平均成本比例扣除，不是照原始買價，所以沒辦法像帳戶餘額那樣單純交給資料庫加總（試算過:同樣的一組買賣交易，換個順序執行，最終的成本基礎會不一樣，證明這確實是路徑相依，不是可以隨便化簡的）。真正的修法是另開一張表存「目前持股狀態」，每次買賣/DCA成交時同步更新，而不是每次都重算全部歷史——這會動到金融資料正確性、且要顧好每個會新增/刪除 `StockTransaction` 的地方都同步更新，需要先跟使用者確認設計才能動工，這輪先不做。

**借貸/代墊列表（`FinanceLoansService.list`/`FinanceAdvancesService.list`）**：查了 LINE 的「借貸列表」「代墊列表」指令才發現，它們需要的是「這個空間**所有**未結清的借貸/代墊」這種完整視圖，不能只看最近 N 筆——但「已結清/未結清」是算出來的（本金減去已還款總和），不是資料庫裡的真實欄位，沒辦法在 SQL `where` 裡直接篩選，除非另外存一個 `settled` 欄位（等於也要做跟持股一樣的快取表）。如果現在硬是照 createdAt 分頁，一筆很久以前欠的錢有可能因為排在分頁後面而從「未結清」清單裡消失不見——這是真的會影響到還沒收回來的錢的正確性風險，所以也先不做，等使用者決定要不要接受「另開一張快取表」這個做法再動工。

`tsc --noEmit`、`flutter analyze`、既有 51 個 API 單元測試全過。
