# 第 2 步：平台總體架構與模組原則

## 一、本階段目標

建立整套平台的總體架構，明確區分：

- 平台核心
- 公司空間
- 獨立功能模組
- Windows 與 LINE 入口
- 自有 API
- 資料隔離
- 跨模組與跨公司資料關聯
- 未來新增公司的方式
- 未來新增功能的方式

本步只確定架構與原則，尚不進入正式程式開發。

---

## 二、第一階段空間範圍

第一階段只建立三個最高層空間：

```text
平台
├── 個人空間
├── 境為室內裝修設計有限公司
└── 張力升建築師事務所
```

目前暫不建立：

- 境泰建設
- 校友會
- 其他公司
- 其他組織
- 跨公司共同專案空間

但底層架構必須保留未來新增公司與組織的能力。

---

## 三、帳號與空間原則

平台採用單一帳號。

同一個使用者可以加入：

- 個人空間
- 境為公司空間
- 建築師事務所空間
- 未來其他公司或組織空間

不同空間的資料、權限與帳務必須隔離。

使用者只能看到自己有權限查看的空間、公司、專案與資料。

---

## 五、Windows 與 LINE 的角色

### Windows

Windows 是第一階段完整操作平台，負責：

- 公司與空間切換
- 完整資料查看
- 新增與編輯資料
- 公司管理
- 權限設定
- 工期表
- 甘特圖
- 成本控制
- 簽核
- 請付款
- 文件管理
- 個人設定

### LINE

LINE 是輕量入口，不是另一套獨立系統。

LINE 主要負責：

- 快速輸入
- 快速查詢
- 通知
- 簡單操作
- 後續可能的表單填寫

Windows 與 LINE 必須共用：

- 同一套帳號
- 同一套權限
- 同一套 API
- 同一套後端
- 同一套資料庫
- 同一套業務邏輯

---

## 六、自有 API 原則

平台的核心 API 由我們自行開發與掌控。

Windows、LINE 與未來其他平台都不得直接連接資料庫。

正確流程為：

```text
Windows 或 LINE
↓
我們自己的 API
↓
登入驗證
↓
權限檢查
↓
業務邏輯
↓
資料庫
```

API 由我們自行定義：

- 網址
- 資料格式
- 權限規則
- 業務流程
- 錯誤處理
- 模組互動方式
- 可執行的操作

可以使用成熟的開源後端框架建立 API，但核心規則不能綁死在第三方平台。

---

## 七、獨立模組原則

以下功能必須是獨立正式模組：

- 簽核系統
- 工期管理
- 成本控制
- 文件管理
- 請款系統
- 付款系統
- 任務系統
- 行事曆
- 專案管理

不能把它們全部寫死在境為公司或某個專案裡。

每間公司可以決定是否啟用。

例如：

```text
境為
├── 專案
├── 工期
├── 成本
├── 文件
├── 採購
├── 簽核
├── 請款
└── 付款
```

```text
建築師事務所
├── 建築專案
├── 設計進度
├── 文件
├── 簽核
├── 請款
└── 付款
```

---

## 八、模組獨立但可互通

模組彼此獨立，但可以透過正式資料關聯互通。

例如廠商請款流程：

```text
建立請款單
↓
送交簽核
↓
簽核完成
↓
建立付款
↓
公司帳戶支出
↓
專案成本增加
↓
付款證明存入文件系統
```

涉及的模組包括：

- 請款
- 簽核
- 付款
- 成本
- 文件

這些不是同一張資料表，也不是同一個功能，但可以透過關聯編號互相連接。

---

## 九、帳戶獨立、金流互通

不同公司與不同帳本必須保持獨立。

例如：

- 個人帳本
- 境為公司帳本
- 建築師事務所帳本
- 專案成本帳

這些帳本不能合併成同一本帳。

但可以建立正式關聯。

### 公司代墊範例

個人付款時：

```text
個人帳本
├── 支出
└── 待報銷
```

公司端：

```text
公司系統
└── 代墊請款紀錄
```

公司付款後：

```text
個人帳本
└── 收入

公司帳本
└── 支出
```

兩邊紀錄互相關聯，但帳本仍然獨立。

### 跨公司交易範例

境為向建築師事務所請款：

```text
境為
└── 應收款
```

```text
建築師事務所
└── 應付款
```

付款完成後，雙方各自產生收入與支出紀錄，並透過同一筆跨公司交易關聯。

---

## 十、公司頁面必須依性質設定

每間公司的首頁、導航與資訊內容不能完全相同。

公司應可以依性質設定：

- 首頁卡片
- 左側導航
- 啟用模組
- 欄位
- 狀態
- 表單
- 簽核流程
- 編號規則
- 文件分類
- 通知規則
- 角色與權限
- Logo
- 主色
- 背景
- 快捷功能

公司頁面不能寫死在程式中。

---

## 十一、新增公司的方式

新增公司分成兩種情況。

### 情況一：全部使用既有模組

如果新公司只需要平台已經存在的功能，新增時應由管理員介面完成。

流程：

```text
新增公司
↓
填寫公司基本資料
↓
選擇公司類型或公司範本
↓
勾選需要啟用的模組
↓
設定首頁與導航
↓
設定角色與權限
↓
完成建立
```

例如可勾選：

- 專案
- 簽核
- 工期
- 文件
- 成本
- 請款
- 付款
- 人資
- 採購
- 任務
- 行事曆

這種情況不需要 Claude Code，也不需要撰寫 MD。

---

## 十二、公司範本

新增公司時，系統可以提供公司範本。

例如：

- 室內設計公司
- 建築師事務所
- 建設公司
- 餐飲公司
- 旅宿公司
- 一般企業
- 空白公司

選擇公司範本後，系統自動預選：

- 建議模組
- 首頁卡片
- 導航
- 基本角色
- 常用流程
- 文件分類

管理員仍可自行增加或取消。

---

## 十三、新增功能的方式

只有當新公司需要平台尚未具備的功能時，才需要撰寫 MD。

例如新增旅宿公司，但平台沒有：

- 房況管理
- 訂房管理
- 房務排程
- 入住
- 退房

此時流程為：

```text
發現平台缺少功能
↓
撰寫新模組需求 MD
↓
由我深化與檢查需求
↓
使用者確認
↓
轉成 Claude Code 開發指令
↓
開發新模組
↓
完成測試與驗收
↓
新模組加入平台模組庫
↓
所有公司都可以選擇是否啟用
```

因此：

> 公司設定透過管理員介面完成；平台缺少新功能時，才使用 MD 開發新模組。

---

## 十四、MD 文件的用途

MD 不再用來建立一般公司設定。

MD 主要用於：

### 新模組需求

例如：

```text
inventory-module.md
hotel-room-module.md
approval-module-extension.md
```

### 跨模組流程需求

例如：

```text
vendor-payment-workflow.md
employee-reimbursement-workflow.md
intercompany-payment-workflow.md
```

MD 是需求與開發文件，不是一般公司的日常設定方式。

## 十六、建築師事務所

建築師事務所仍使用相同的平台核心與共用模組。

但其公司首頁、導航與實際模組內容，將依建築師事務所的業務性質另行規劃。

目前不先把建築師事務所功能寫死。

---

## 十七、AI 範圍

第一階段完全排除 AI 功能。

暫不開發：

- AI 對話
- AI 搜尋
- AI 分類
- AI 摘要
- AI 記憶
- AI 分析
- AI 自動操作
- AI API

底層可以避免封死未來擴充空間，但目前不串接、不使用、不付費。

---

## 十八、費用揭露原則

任何開發步驟若涉及費用，必須提前說明。

包括：

- API 服務
- VPS
- 雲端伺服器
- 資料庫
- 檔案儲存
- 網域
- SSL
- LINE 官方帳號
- 訊息費用
- 第三方服務
- 開發工具訂閱
- 備份
- 流量
- 其他付費功能

每次必須列出：

- 是否必要
- 一次性費用
- 每月費用
- 依使用量費用
- 免費額度
- 免費替代方案
- 何時可能開始收費

未經使用者明確同意，不採用新的付費服務。

---

## 十九、第 2 步正式原則

1. 第一階段只建立個人、境為、建築師事務所三個空間。
2. 使用者以單一帳號加入不同空間。
3. 各空間資料、權限與帳務必須隔離。
4. Windows 是完整操作入口。
5. LINE 是輕量輸入、查詢與通知入口。
6. Windows 與 LINE 共用同一套後端、API 與資料庫。
7. 平台核心 API 由我們自行開發。
8. Windows 與 LINE 不得直接連接資料庫。
9. 簽核、工期、成本、文件、請款、付款都是獨立模組。
10. 各模組可被不同公司啟用。
11. 模組彼此獨立，但可透過關聯資料與流程互通。
12. 公司與帳戶保持獨立，但金流可以正式關聯。
13. 公司頁面依公司性質設定，不可寫死。
14. 新增公司時，可選擇公司範本與既有模組。
15. 使用既有模組新增公司時，不需要 MD，也不需要修改程式。
16. 平台缺少新功能時，才撰寫新模組需求 MD。
17. 新模組完成後，加入平台模組庫，供所有公司選擇啟用。
18. 第一階段排除所有 AI 功能。
19. 所有可能產生費用的服務必須事前揭露並取得同意。
20. 本步完成後，才進入下一階段的技術選型與資料架構規劃。
