## 2026-07-24：Google 登入 / 密碼登入全部 500，且登入狀態不會保留

**使用者回報**：
1. 用 Google 無法登入
2. 希望 Google 登入的使用者只要沒登出，重開 App 不用再登入一次

**讀到的資訊**：
- 登入畫面截圖顯示 `Internal server error`（NestJS 對未攔截例外的預設訊息，代表後端某個地方直接炸掉，不是正常的驗證失敗訊息）
- 用不存在的帳號名稱測試 `/auth/login`（不需要真實帳密，任何查詢 User 資料表的動作都會踩到同一個問題）也回 500，代表連「查無此帳號」的正常錯誤路徑都跑不到，卡在資料庫查詢那一步
- Render 的 `Logs` 頁面關鍵字：`PrismaClientKnownRequestError`、`Authentication failed against the database server`、`password authentication failed for user "postgres"`、`code: 'P1000'`、`kind: 'AuthenticationFailed'`

**根本原因（其實是兩個疊在一起）**：
1. 當次部署新增了 `User.isPlatformAdmin` 欄位的 migration，但 Render 的部署流程**不會自動執行 `prisma migrate deploy`**——過去的 migration 是透過人工在有正式環境資料庫連線的情況下手動跑的，這次沒有人做這一步，所以正式環境資料庫其實沒有這個欄位。後來直接用 Supabase 的 Session Pooler 連線字串在本機跑 `npx prisma migrate deploy` 補上。
2. 為了要到連線字串，請使用者去 Supabase 重設了資料庫密碼，但 **Render 的 `DATABASE_URL` 環境變數不會跟著自動更新**，導致重設密碼之後 Render 端反而用舊密碼連不上（新的問題疊加在原本的問題上，一開始沒發現）。修正時又額外卡了兩個「人為操作」陷阱：
   - 編輯 Render 環境變數後，忘記按最下面的 **Save, rebuild, and deploy** 按鈕，改了等於沒改
   - 複製貼上連線字串時，密碼跟主機中間的 `@` 符號在貼上過程中遺失（`...Aq8Jaws-0-...` 少了一個 `@`），造成連線字串格式錯誤

**確認方式**：
- 直接用使用者提供的 Session Pooler 連線字串，在本機分別用 raw `pg` client 跟正式的 Prisma Client（同一份 generated client）連正式資料庫測試查詢，用來排除「是資料庫本身壞了」還是「只有 Render 那邊連不上」
- 用 `curl` 打 `/auth/login`（帶不存在的帳號）當作免帳密的健康檢查，重複測試不需要每次都等使用者操作 App

**最終解法**：
1. 本機執行 `DATABASE_URL="<正式環境連線字串>" npx prisma migrate deploy`（在 `apps/api` 目錄下）補上遺漏的 migration
2. 到 Render 後台 → `life-os-api` 服務 → Environment，把 `DATABASE_URL` 更新成當下正確的 Supabase Session Pooler 連線字串（`postgresql://postgres.<project-ref>:<密碼>@aws-0-<region>.pooler.supabase.com:5432/postgres`），存檔時務必點擊 **Save, rebuild, and deploy**（不是只按 Edit 旁邊那個沒有文字的存檔圖示）
3. 重新部署後用 `curl` 打 `/auth/login` 確認回應從 500 變成正常的 401「帳號密碼錯誤」

**以後遇到類似狀況可以先查**：
- 只要 Render log 出現 `password authentication failed` 或 `P1000`，先去 Environment 頁面把 `DATABASE_URL` 完整展開讀一次，不要只看有沒有存在，要逐字確認使用者名稱、密碼、`@`、主機名稱都在
- Supabase 重設資料庫密碼**不會**自動同步到任何外部服務（Render、本機 `.env` 等），改密碼之後要記得手動更新每一個用到這組連線字串的地方
- schema 有變更時，記得這個專案的 migration **不是**部署時自動套用的，要自己手動用正式環境連線字串跑 `prisma migrate deploy`（或未來考慮把它加進 Render 的 build/start command，一勞永逸解決這個坑）

**後續（同一天）：把 migration 自動化，避免以後再漏掉**

原本想用 Render 的 **Pre-Deploy Command**（Settings → Deploy，官方就是設計給 migration 用的），但這個欄位**免費方案是鎖住的**（"available for paid instances only"）。改成把它接到 **Start Command** 前面：

- 改之前：`node dist/src/main.js`
- 改之後：`npx prisma migrate deploy && node dist/src/main.js`

這樣每次 App 啟動（包含免費方案閒置後被喚醒的每一次重啟）都會先確認 migration 是不是最新的，沒有新的要套用時幾乎不花時間，不會影響啟動速度。改完後續就不用再手動跑 migrate deploy 了——新增 migration 只要正常 `git push`，下次部署/重啟就會自動套用。

## 2026-07-26：「測試」專案的專案資料截圖（螢幕擷取畫面 2026-07-26 013132.png）

**讀到的資訊**：截圖是「境為室內裝修設計」空間下「測試」專案的「專案資料」分頁，顯示類型/狀態（未分類）、業主名稱（塵封竹）、專案地點/案號（空白）、預計結案日（2026/7/31）、開工日（2026/7/24），畫面正常渲染、沒有錯誤訊息或崩潰。

**判斷**：檔案時間是 01:31，早於同一天稍晚（23:18）才提交的「預計結案日 field + 合約寫回 + 排程警示」那個 commit，代表這張截圖是那次開發階段中途、功能還沒收尾時存的，不是使用者事後回報的錯誤——後續同一個 session 已經把預計結案日欄位、開工日改稱簽約日期、日期欄位樣式統一等都做完並收進去了。這次（產出 大系統V1.10.0 前）檢查沒有發現截圖對應到任何尚未解決的問題，故直接清除。

**以後遇到類似狀況可以先查**：截圖檔名的時間戳記可以拿來跟 `git log` 對照，判斷截圖是開發中途的存檔還是真的事後回報的錯誤，避免把已經解決的東西當成新問題重查一次。

## 2026-07-27：工期表「工項名稱」欄位標題跟下面實際欄位對不齊（螢幕擷取畫面 2026-07-26 212503.png）

**使用者回報**：工進表屬性名稱的欄位跟下面實質寬度不一樣（原本在已刪除的 reno_pm 專案上發現，確認 life_os 的工期表是同一份程式碼移植過來的，也有一樣的問題）。

**讀到的資訊**：截圖是「境為室內裝修設計」空間「測試」專案的「工期」分頁，可以看到表頭「工項名稱」文字明顯比下面每一列的實際輸入框內容更靠左，連帶「起始日」「結束日」「工期(天)」「相依」這幾欄的表頭文字也整體比下面欄位偏左，跟資料對不齊。

**根本原因**：`apps/windows_app/lib/ui/widgets/projects/task_table/task_table.dart`。表頭 Row 在「工項名稱」欄位前只留了 `SizedBox(width: 12)`；但每一列的資料 Row 在名稱欄位前實際上排了拖曳把手圖示(16) + 收合按鈕欄位(18) + 顏色色條(4) + 間距(8) = 46px。表頭跟資料列的「前導留白」寬度差了 34px，導致名稱欄位（以及後面所有固定寬度欄位）表頭跟實際內容整排錯位。

**確認方式**：讀原始碼比對表頭 Row（第 154-192 行）跟資料列 `_TaskRow` 的 Row（第 432-598 行）在「工項名稱」欄位前各自排了哪些子元件、加總寬度。

**最終解法**：新增共用常數 `_leadingGutterWidth = 16.0 + 18.0 + 4.0 + 8.0`（16+18+4+8，數字對應資料列前導元件的寬度），把表頭原本的 `SizedBox(width: 12)` 換成 `SizedBox(width: _leadingGutterWidth)`，讓表頭跟深度 0 的資料列前導留白寬度一致。`flutter analyze` 乾淨、`flutter build windows --release` 成功。發布為 v0.11.2。

**以後遇到類似狀況可以先查**：這個表格的表頭 Row 跟資料列 Row 是兩個獨立寫死的 Row，沒有共用一份欄位寬度定義（各欄位資料寬度雖然共用 `_ColumnWidths`/`widths` 物件，但「名稱欄位前面留多少空白」這件事表頭跟資料列各自寫死常數）。以後如果要調整資料列名稱欄位前面的拖曳把手/收合按鈕/色條/間距寬度，要記得同步更新 `_leadingGutterWidth`，否則同樣的錯位問題會再出現一次。
