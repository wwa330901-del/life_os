## 2026-07-24：Google 登入 / 密碼登入全部 500，且登入狀態不會保留

**使用者回報**：
1. 用 Google 無法登入
2. 希望 Google 登入的使用者只要沒登出，重開 App 不用再登入一次

**讀到的資訊**：
- 登入畫面截圖顯示 `Internal server error`（NestJS 對未攔截例外的預設訊息，代表後端某個地方直接炸掉，不是正常的驗證失敗訊息）
- 用不存在的帳號名稱測試 `/auth/login`（不需要真實帳密，任何查詢 User 資料表的動作都會踩到同一個問題）也回 500，代表連「查無此帳號」的正常錯誤路徑都跑不到，卡在資料庫查詢那一步
- Render 的 `Logs` 頁面關鍵字：`PrismaClientKnownRequestError`、`Authentication failed against the database server`、`password authentication failed for user "postgres"`、`code: 'P1000'`、`kind: 'AuthenticationFailed'`

**根本原因（其實是兩個疊在一起）**：
1. 當次部署新增了 `User.isPlatformAdmin` 欄位的 migration，但 Render 的部署流程**不會自動執行 `prisma migrate deploy`**——過去的 migration 是透過人工在有正式環境資料庫連線的情況下手動跑的，這次沒有人做這一步，所以正式環境資料庫其實沒有這個欄位。後來直接用 Supabase 的 Session Pooler 連線字串在本機跑 `npx prisma migrate deploy` 補上。
2. 為了要到連線字串，請使用者去 Supabase 重設了資料庫密碼，但 **Render 的 `DATABASE_URL` 環境變數不會跟著自動更新**，導致重設密碼之後 Render 端反而用舊密碼連不上（新的問題疊加在原本的問題上，一開始沒發現）。修正時又額外卡了兩個「人為操作」陷阱：
   - 編輯 Render 環境變數後，忘記按最下面的 **Save, rebuild, and deploy** 按鈕，改了等於沒改
   - 複製貼上連線字串時，密碼跟主機中間的 `@` 符號在貼上過程中遺失（`...Aq8Jaws-0-...` 少了一個 `@`），造成連線字串格式錯誤

**確認方式**：
- 直接用使用者提供的 Session Pooler 連線字串，在本機分別用 raw `pg` client 跟正式的 Prisma Client（同一份 generated client）連正式資料庫測試查詢，用來排除「是資料庫本身壞了」還是「只有 Render 那邊連不上」
- 用 `curl` 打 `/auth/login`（帶不存在的帳號）當作免帳密的健康檢查，重複測試不需要每次都等使用者操作 App

**最終解法**：
1. 本機執行 `DATABASE_URL="<正式環境連線字串>" npx prisma migrate deploy`（在 `apps/api` 目錄下）補上遺漏的 migration
2. 到 Render 後台 → `life-os-api` 服務 → Environment，把 `DATABASE_URL` 更新成當下正確的 Supabase Session Pooler 連線字串（`postgresql://postgres.<project-ref>:<密碼>@aws-0-<region>.pooler.supabase.com:5432/postgres`），存檔時務必點擊 **Save, rebuild, and deploy**（不是只按 Edit 旁邊那個沒有文字的存檔圖示）
3. 重新部署後用 `curl` 打 `/auth/login` 確認回應從 500 變成正常的 401「帳號密碼錯誤」

**以後遇到類似狀況可以先查**：
- 只要 Render log 出現 `password authentication failed` 或 `P1000`，先去 Environment 頁面把 `DATABASE_URL` 完整展開讀一次，不要只看有沒有存在，要逐字確認使用者名稱、密碼、`@`、主機名稱都在
- Supabase 重設資料庫密碼**不會**自動同步到任何外部服務（Render、本機 `.env` 等），改密碼之後要記得手動更新每一個用到這組連線字串的地方
- schema 有變更時，記得這個專案的 migration **不是**部署時自動套用的，要自己手動用正式環境連線字串跑 `prisma migrate deploy`（或未來考慮把它加進 Render 的 build/start command，一勞永逸解決這個坑）

**後續（同一天）：把 migration 自動化，避免以後再漏掉**

原本想用 Render 的 **Pre-Deploy Command**（Settings → Deploy，官方就是設計給 migration 用的），但這個欄位**免費方案是鎖住的**（"available for paid instances only"）。改成把它接到 **Start Command** 前面：

- 改之前：`node dist/src/main.js`
- 改之後：`npx prisma migrate deploy && node dist/src/main.js`

這樣每次 App 啟動（包含免費方案閒置後被喚醒的每一次重啟）都會先確認 migration 是不是最新的，沒有新的要套用時幾乎不花時間，不會影響啟動速度。改完後續就不用再手動跑 migrate deploy 了——新增 migration 只要正常 `git push`，下次部署/重啟就會自動套用。

## 2026-07-27：工期表「工項名稱」欄位標題跟下面實際欄位對不齊（螢幕擷取畫面 2026-07-26 212503.png）

**使用者回報**：工進表屬性名稱的欄位跟下面實質寬度不一樣（原本在已刪除的 reno_pm 專案上發現，確認 life_os 的工期表是同一份程式碼移植過來的，也有一樣的問題）。

**讀到的資訊**：截圖是「境為室內裝修設計」空間「測試」專案的「工期」分頁，可以看到表頭「工項名稱」文字明顯比下面每一列的實際輸入框內容更靠左，連帶「起始日」「結束日」「工期(天)」「相依」這幾欄的表頭文字也整體比下面欄位偏左，跟資料對不齊。

**根本原因**：`apps/windows_app/lib/ui/widgets/projects/task_table/task_table.dart`。表頭 Row 在「工項名稱」欄位前只留了 `SizedBox(width: 12)`；但每一列的資料 Row 在名稱欄位前實際上排了拖曳把手圖示(16) + 收合按鈕欄位(18) + 顏色色條(4) + 間距(8) = 46px。表頭跟資料列的「前導留白」寬度差了 34px，導致名稱欄位（以及後面所有固定寬度欄位）表頭跟實際內容整排錯位。

**確認方式**：讀原始碼比對表頭 Row（第 154-192 行）跟資料列 `_TaskRow` 的 Row（第 432-598 行）在「工項名稱」欄位前各自排了哪些子元件、加總寬度。

**最終解法**：新增共用常數 `_leadingGutterWidth = 16.0 + 18.0 + 4.0 + 8.0`（16+18+4+8，數字對應資料列前導元件的寬度），把表頭原本的 `SizedBox(width: 12)` 換成 `SizedBox(width: _leadingGutterWidth)`，讓表頭跟深度 0 的資料列前導留白寬度一致。`flutter analyze` 乾淨、`flutter build windows --release` 成功。發布為 v0.11.2。

**以後遇到類似狀況可以先查**：這個表格的表頭 Row 跟資料列 Row 是兩個獨立寫死的 Row，沒有共用一份欄位寬度定義（各欄位資料寬度雖然共用 `_ColumnWidths`/`widths` 物件，但「名稱欄位前面留多少空白」這件事表頭跟資料列各自寫死常數）。以後如果要調整資料列名稱欄位前面的拖曳把手/收合按鈕/色條/間距寬度，要記得同步更新 `_leadingGutterWidth`，否則同樣的錯位問題會再出現一次。

## 2026-07-28：裝了新安裝檔，App 內建的「檢查更新」還是一直說要更新到 v0.13.0

**使用者回報**：「我更新了四次他還是不斷重複要我更新v0.13.0」——照installer裝了好幾次，開起來還是跳出「有新版本 v0.13.0」的提示，裝了也沒用。

**讀到的資訊**：用 PowerShell 直接讀剛編出來的 `life_os_app.exe` 的 `VersionInfo`（`(Get-Item ...).VersionInfo`），發現明明 `pubspec.yaml` 已經改成 `0.13.0+1`，`flutter build windows --release` 编出來的 exe 內嵌版本卻還停在 `0.12.0+1`——也就是說，App 內建更新檢查（`update_service.dart` 用 `package_info_plus` 讀這個 exe 的內嵌版本號去跟 GitHub 最新 Release tag 比對）讀到的「目前版本」根本沒真的更新，永遠比 GitHub 上的新版舊，才會裝了幾次都還一直跳更新提示。

**根本原因**：Flutter 的 Windows build 是透過 CMake 產生 `Runner.rc`（版本資源）的，但這一步只有在 CMake 判斷「需要重新產生」時才會跑；用一般的 `flutter build windows --release`（沒清掉舊的 `build/windows` 資料夾）屬於增量編譯，CMake 沒偵測到需要重跑版本產生這一步，導致版本號被凍結在很久以前第一次編譯時的數字，即使 `pubspec.yaml` 已經改了、程式碼也確實改了，只有「版本號」這個資源沒有跟著更新。這代表這一輪之前發布的 v0.11.2/v0.12.0 安裝檔，很可能也帶著同樣過期的內嵌版本號（只是沒被發現，因為使用者剛好還沒進到會觸發這個症狀的情境）。

**確認方式**：`(Get-Item "...\life_os_app.exe").VersionInfo | Select FileVersion,ProductVersion` 比對 `pubspec.yaml` 的版本，裝完前後各查一次。

**最終解法**：`rm -rf apps/windows_app/build/windows` 清掉整個 build 目錄，強迫 CMake 從頭跑一次（會重新產生版本資源），再 `flutter build windows --release`，這次編出來的 exe 版本正確顯示 `0.13.0+1`。重新打包安裝檔後用 `gh release upload v0.13.0 <exe> --clobber` 覆蓋掉原本版本號有問題的那個安裝檔資產（沒有另外開新版號，因為程式碼本身沒有變，只是重新編譯讓版本號正確）。

**以後遇到類似狀況可以先查**：**每次發布新版之前，`flutter build windows --release` 前一定要先清掉 `apps/windows_app/build/windows`（或至少確認 `(Get-Item build\windows\x64\runner\Release\life_os_app.exe).VersionInfo.FileVersion` 真的等於 `pubspec.yaml` 的版本），不能只信任增量編譯會自動抓到版本號變更。**這條要補進「六、發布流程」的標準步驟，以後每次 bump 版本號都要照做，不要再漏掉。reno_pm（已刪除）當初可能也有同樣的隱性 bug，只是沒被追出來過。

## 2026-07-29：文件預覽/PDF/列印跳出「找不到 LibreOffice」（螢幕擷取畫面 2026-07-28 211450.png）

**使用者回報**：專案文件（相關文件分頁）無法預覽。

**讀到的資訊**：截圖顯示點「已產生的文件」項目後，畫面下方跳出提示「找不到 LibreOffice，請先安裝（libreoffice.org）後再試一次」。

**使用者回報**：截圖 Supabase 寄的資安警告信「Action required: security vulnerabilities detected in your projects」，內容是某張表 `r1s_disabled_in_public`——沒開 RLS，任何人拿到專案網址就能讀寫刪那張表的全部資料。

**判斷過程**：
1. 先確認曝光範圍：全repo搜尋 `supabase`／`SUPABASE`，確認 Windows App 跟 NestJS API 完全沒有用 supabase-js 或 anon key，`apps/api/prisma/schema.prisma` 的 datasource 是直接 `postgresql://` 連線字串——代表正常情況下使用者只會透過 NestJS API 存取資料，Supabase 自動產生的 PostgREST REST API 是完全沒被用到、但預設仍是開著的旁路，沒開 RLS 就等於這條旁路對外全開。
2. 因為 Prisma 是用資料表擁有者身分直連（`prisma migrate deploy` 建表的那個角色），Postgres 的規則是**擁有者預設會繞過 RLS**（除非額外下 `FORCE ROW LEVEL SECURITY`），所以幫全部資料表開 RLS、不加任何 policy，只會擋掉 PostgREST 匿名/認證角色的存取，不會影響 NestJS 本身的 Prisma 連線。

**解法**：新增 migration `apps/api/prisma/migrations/20260801190000_enable_row_level_security/migration.sql`，對 `schema.prisma` 裡全部 28 個 model 對應的資料表下 `ALTER TABLE "X" ENABLE ROW LEVEL SECURITY;`（不加 policy，預設對非擁有者全部拒絕）。確認過 Render 的 Start Command 已經是 `npx prisma migrate deploy && node dist/src/main.js`（見上面 2026-07-24 那則的後續修正），所以只要正常 `git push`，下次部署/重啟就會自動套用，不需要手動連正式環境資料庫跑指令。

**以後遇到類似狀況可以先查**：
- Supabase 資安信只會列出「目前發現的」那幾張表，不代表只有那幾張有問題——新增資料表時養成習慣同一輪順手把新表也加進 RLS migration，不要等下一封警告信才補。
- 這個專案完全不用 Supabase 的 PostgREST／anon key，純粹把 Supabase 當一般 Postgres 代管服務用——如果以後真的要讓前端直連 Supabase（不經過 NestJS），開 RLS 之後要記得同時寫對應的 policy，不能只靠「不加 policy＝全擋」。

**解法**：討論到一半使用者直接定調新規則（見 `new/大系統V1.32.0.md` 完整記錄）——每筆代辦事項的時間屬性必須是「日期」或新增的「持續性任務」（`isOngoing`）欄位二選一，不能都不選。純應用層驗證（`TodosService.assertDueDateXorOngoing`），沒加 DB constraint，舊資料（兩者都沒有）明確不強制補值、維持原樣。總覽新增第四分類「持續性任務」，永遠列出不受 7 天窗口限制。LINE「新增」指令現在要求帶日期（`新增 8/10 買材料`）或「持續」關鍵字（`新增 持續 每週檢查庫存`），兩者都沒偵測到就直接請使用者補上。

**以後遇到類似狀況可以先查**：
- 使用者回報「這個功能好像沒生效／沒更新」時，先查有沒有「記住上次選擇/狀態」的機制在擋（`activeProjectId`、`activeTodoPersonal` 這類欄位）——這種情況下程式碼其實已經部署成功，只是使用者的既有狀態繞過了新加的分岔點，不是部署失敗。
- 任何「用日期/時間窗口篩選要不要顯示」的清單邏輯（像這裡的總覽），都要想清楚「完全沒有日期」的項目該落在哪裡——沒有明確歸屬的分類，等於永遠不會出現，這類窗口式篩選最容易漏掉「無日期」這個邊界情況。

## 2026-08-04：首頁「本日代辦事項」看不到今天到期的項目（口頭回報）

**讀到的資訊**：使用者截圖顯示代辦事項空間裡有兩筆截止當天（8/4）的個人事項，但首頁「本日代辦事項」小工具卻顯示「今日到期未完成（0）」。回報時間是台灣時間凌晨兩點多。

**判斷過程**：查到 `HomeService.todayRange()` 用 `new Date()` 配 `getFullYear/getMonth/getDate()` 算「今天」的起訖時間，完全沒有處理時區——伺服器（Render）系統時區是 UTC，台灣時間 00:00～08:00 這段，UTC 都還停在前一天，伺服器算出來的「今天」範圍會整整晚台灣一天，導致代辦事項的 `dueDate`（以 UTC 午夜儲存）落在誤判的範圍之外。全文搜尋後發現 `LineService` 的「財務總覽」今日收支、「代辦事項總覽」今日到期/未來 7 天，也是同樣的寫法、同樣的問題。

**解法**：新增共用工具 `apps/api/src/common/taipei-date.ts`（`taipeiTodayRange`/`taipeiCurrentMonth`），用「先加 8 小時再取 UTC 年月日」的技巧算出台灣真正的今天範圍，不管伺服器自己的系統時區是什麼都正確。三個受影響的地方全部改用這個共用工具。詳見 `new/大系統V1.37.0.md`。

**以後遇到類似狀況可以先查**：
- 這個專案已經在好幾個地方踩過「伺服器是 UTC，沒特別處理就以為是台灣時間」的坑（`@Cron` 沒指定 `timeZone`、行事曆全天事件跨日），這次是同一類問題出現在「今天」這個時間窗口的計算上。**任何新寫的「今日 XXX」邏輯，只要用到 `new Date()` 加 `getFullYear/getMonth/getDate()` 算當天範圍，都要改用 `taipeiTodayRange()`，不要再手刻一次**——這個 bug 很難被一般測試發現，因為只有台灣時間 00:00～08:00 這段才會出錯，白天測試完全正常。

## 2026-08-05：一張截圖（股票「交易紀錄」分頁讀取失敗，type cast 錯誤）

**讀到的資訊**：App 投資→交易紀錄分頁顯示紅字「讀取股票交易失敗：type '_Map<String, dynamic>' is not a subtype of type 'List<dynamic>' in type cast」。

**判斷過程**：這不是新寫的程式碼本身有 bug——查了當時最新的 `api_client.dart`，`listStockTransactions` 早就正確改成 `_get` + `StockTransactionsPage.fromJson`，跟後端 v2.9.4 把 `GET /spaces/:spaceId/stocks/transactions` 的回傳格式從純陣列改成 `{ items, nextCursor }`（游標分頁，見 `新增大系統V1.46.0.md`）完全對得上。問題出在**部署時間差**：後端部署在 Render，git push 之後幾乎立刻自動重新部署上線；但 Windows App 是要使用者自己重新安裝新版安裝檔才會更新。使用者當下用的是**還沒更新到 v2.9.4 的舊版 App**，裡面的舊程式碼還在用 `_getList`（預期收到陣列）去打「已經是新格式」的後端——舊 App 收到 `{items:...}` 物件、拿去當陣列強制轉型，就是這個錯誤訊息的由來。錯誤方向（Map 轉 List 失敗，不是 List 轉 Map 失敗）正好印證了「App 舊、後端新」這個方向，不是反過來。

**解法**：請使用者更新 Windows App 到 v2.9.4（重開 App 讓內建更新檢查跳出來，或直接跑新安裝檔）即可恢復正常，後端本身沒有問題、不用改任何程式碼。

**以後遇到類似狀況可以先查**：
- **任何一次改動既有 API 端點的回傳格式**（不是新增端點，是改掉一個原本就在用的端點的資料形狀，例如陣列→分頁物件），部署後端（Render 自動部署）跟使用者實際更新 Windows App 之間永遠有一段時間差——這段期間舊 App 打新後端一定會出型別轉換錯誤。**發布這類「改格式」的更新時，應該在回報訊息裡明確提醒使用者「這次後端格式有變、記得盡快更新 App」**，收到「讀取 XX 失敗：type cast」這種錯誤時，第一個該懷疑的不是新程式碼寫錯，而是先問使用者「App 版本是不是還沒更新到最新」。

## 2026-08-05：一張截圖（持股總覽全部顯示「尚無報價」，判斷為非 bug）

**讀到的資訊**：使用者更新到 v2.9.4 後，App 投資→持股總覽的每一檔股票（0050/0056/00878/00919）市值/損益都顯示「（尚無報價）」，總計的「目前市值」「損益」也是「（無報價）」。截圖時間約台灣時間 13:51（週三）。

**判斷過程**：查 `StocksPriceService`——收盤價 cron 只在平日 14:30 跑一次，盤中即時價 cron 只在平日 09:00–13:30 每 5 分鐘跑一次，而且兩個 cron 都只抓「目前有交易紀錄或有效定期定額」的股票代碼（`trackedStockCodes()`），不會對整個台股清單發請求。這幾檔股票是使用者剛剛才補登歷史持股用的交易（見稍早關於「補目前持股」的討論），代碼是**這次交易存進去之後才第一次被納入追蹤範圍**——今天稍早的盤中報價 cron 跑的時候這些代碼根本還不存在，自然抓不到。截圖當下（13:51）已經過了 13:30 的盤中報價收工時間，還沒到 14:30 的收盤價更新時間，所以現在這個當下任何股票代碼（不只新增的）本來就都不會有報價更新——這是排程時間點卡在中間的正常空窗，不是 bug。

**判斷結論**：不用改任何程式碼。使用者今天 14:30 之後回頭看，收盤價 cron 跑過一次，這幾檔就會顯示報價/市值/損益了；之後每個交易日盤中每 5 分鐘、收盤後都會持續更新。

**以後遇到類似狀況可以先查**：
- 股票報價是「目前有追蹤的代碼」才會抓，新增一筆從沒出現過的股票代碼之後，要等到下一次排定的 cron 時間（盤中 9:00–13:30 每 5 分鐘、或平日 14:30 收盤）才會第一次有報價，中間這段空窗期顯示「尚無報價」是正常的，不是「補登資料失敗」。回報「XX 沒有報價/市值」時，先看回報時間是不是剛好卡在 13:30～14:30 這種排程空窗，或代碼是不是剛剛才第一次出現。
